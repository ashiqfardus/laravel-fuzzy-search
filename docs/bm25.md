## BM25 Inverted Index

For large tables (10k+ rows), the BM25 inverted index provides ranked, fast results without scanning the full table.

### How It Works

The indexing system has two parts:

**Part 1 — One-time initial build.** Run once after install (or after a schema change):

```bash
php artisan fuzzy-search:rebuild "App\Models\User" --fresh
```

**Part 2 — Automatic incremental updates.** Once `indexing.enabled` is `true` (it ships `false`; see [Production Setup](#production-setup)), every time a model is saved or deleted, the package dispatches a small queue job that re-indexes just that one row. No cron jobs or manual work needed.

The job is dispatched once the save's transaction commits (a rolled-back save indexes nothing). Writes for the same row wait for each other on the database, so an overlap can never count a row twice; an error in a synchronous index write is reported through your exception handler, not thrown from `save()`. Writes that fire no Eloquent events are not seen: `Model::query()->update()`, `insert()`, a query-builder `delete()`, `saveQuietly()`, `Model::withoutEvents()` and raw SQL. Re-index rows written this way with `fuzzy-search:rebuild`. A plain rebuild only reads the rows the model's query returns, so it does not remove a row such a write deleted, trashed or moved out of a global scope. For those, run `fuzzy-search:rebuild --fresh`, or `IndexModelJob::dispatch(Model::class, $id)` per row: the job removes a row that is gone.

The flow when a record is saved:

```
User::create(['name' => 'John'])
  → Eloquent fires 'saved' event
  → once the transaction commits, SearchableIndexingObserver dispatches IndexModelJob to queue
  → queue worker claims the row's index entry, re-reads the row and indexes it as stored
  → 'john' is now in the index
```

The indexer indexes the row as it is stored at that moment, not the instance that was saved: whichever write commits last leaves the latest save indexed, and a row that is gone, soft-deleted or hidden by the model's global scopes leaves the index. The Scout engine's `update()` reads the row as Scout's own jobs do instead (see [Scout Driver](integrations.md#scout-driver)). Under heavy contention a write that hits a deadlock is tried up to three times; one that loses all three is retried by the queue (`indexing.async`) or reported to your exception handler (sync).

**Constraints are honoured on the index path.** Filters, `where()` constraints applied before the search, and global scopes are checked against the ranking in chunks (`bm25.candidate_chunk`, default 200) until the page is full, and `paginate()` totals reflect them:

```php
Product::search('watch')
    ->useInvertedIndex()
    ->filter('published', true)
    ->paginate(20);   // total = published matches only, pages never come back short

// Equivalent — filter()/filterIn() still work, but constraints can also be chained
// straight onto the builder (see [Chaining Eloquent](../README.md#chaining-eloquent)):
Product::search('watch')
    ->useInvertedIndex()
    ->where('published', true)
    ->paginate(20);
```

`_score` is scaled against the best-ranked row the query can see, so under constraints the top result scores `1` and a row the query hides never sets the scale. `_raw_score` is the unscaled BM25 value: its IDF and average document length come from the model's whole index, so on a shared multi-tenant index they count every tenant's rows. Leave `_raw_score` out of a response when one tenant must not learn anything about another's vocabulary.

### Database Tables

| Table | Purpose |
| --- | --- |
| `fuzzy_index_terms` | Term dictionary: unique terms (at most 191 characters) and how many documents, across every indexed model, hold each one. It orders `didYouMean()` and the typo and prefix expansions. BM25's idf counts documents per model from the postings instead. |
| `fuzzy_index_postings` | Postings: term → model mapping with term frequency, one row per `(term, column)` |
| `fuzzy_index_meta` | BM25 normalization: total docs + avg document length per model |
| `fuzzy_index_documents` | Per-document length cache for O(1) BM25 scoring |

### Production Setup

**Step 1 — Run migrations:**

```bash
php artisan migrate
```

**Step 2 — Enable indexing in config:**

```php
// config/fuzzy-search.php
'indexing' => [
    'enabled'          => true,       // must be true or saves are never indexed
    'async'            => true,       // true = queued (recommended for production)
    'queue'            => 'indexing', // dedicated queue keeps indexing isolated
    'chunk_size'       => 500,
    'max_tokens_per_doc' => 5000,     // security cap: prevents index poisoning
],
```

**Step 3 — Declare searchable columns on your model:**

```php
use Ashiqfardus\LaravelFuzzySearch\Traits\Searchable;

class User extends Model
{
    use Searchable;

    protected array $searchable = [
        'columns' => [
            'name'  => 10,
            'email' => 5,
            'bio'   => 2,
        ],
    ];
}
```

**Step 4 — Build the initial index:**

```bash
# For small tables (< 50k rows)
php artisan fuzzy-search:rebuild "App\Models\User" --fresh

# For large tables (50k+ rows), dispatch batch queue jobs
php artisan fuzzy-search:rebuild "App\Models\User" --fresh --async --queue=indexing
```

`--async` needs Laravel's `job_batches` table: `php artisan make:queue-batches-table` (Laravel 10: `php artisan queue:batches-table`), then `php artisan migrate`.

**Step 5 — Start a queue worker:**

```bash
# Development
php artisan queue:work --queue=indexing,default

# Production (Supervisor)
```

Supervisor config (`/etc/supervisor/conf.d/fuzzy-search-worker.conf`):

```ini
[program:fuzzy-search-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/html/artisan queue:work database --queue=indexing,default --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
user=www-data
numprocs=2
redirect_stderr=true
stdout_logfile=/var/log/fuzzy-search-worker.log
```

**SQL Server:** turn on `READ_COMMITTED_SNAPSHOT` for the database (`ALTER DATABASE … SET READ_COMMITTED_SNAPSHOT ON`), or set `scout.after_commit` to `true`, which defers Scout's own save and delete hooks until the commit. The indexer re-reads a row after it claims the row's index entry. Under SQL Server's default locking read committed, that read waits on a row another transaction has updated but not committed. That transaction may be one that indexes before it commits: Scout with `after_commit` off and no queue, or `searchable()` inside `DB::transaction()`. Its index write in turn waits on the claim, so the two deadlock (error 1205). Snapshot reads do not wait. A `searchable()` you call yourself inside `DB::transaction()` still indexes at once, whatever `after_commit` says: call it after the commit, or turn on `READ_COMMITTED_SNAPSHOT`. If you run with `XACT_ABORT ON`, an index write that meets a new word (or a model's first document or meta row) that another write inserted at the same moment fails and is retried by the queue (or reported, when sync) instead of updating that row in place.

For **Laravel Horizon** (Redis):

```php
// config/horizon.php
'environments' => [
    'production' => [
        'supervisor-1' => [
            'connection' => 'redis',
            'queue'      => ['indexing', 'default'],
            'balance'    => 'auto',
            'processes'  => 4,
        ],
    ],
],
```

### Usage

```php
// BM25 search — faster + better relevance on large tables
$users = User::search('john')->useInvertedIndex()->get();

// didYouMean() reads the term dictionary (no scan of your table)
$suggestions = User::search('jonh')->didYouMean(3);
```

`orderBy()` on the builder replaces the BM25 rank order. The page is then the first matches in that order, ties broken by the primary key ascending. The query keeps its select list, so you can order by a `withCount()` or `selectRaw()` alias. The ordered query reads only matching rows. When there are up to `bm25.candidate_chunk` matches (200 by default), it is restricted to their ids. Past that, a subquery on `fuzzy_index_postings` restricts it; that subquery binds the model type and the query's terms, never a list of ids. On MySQL and MariaDB it compares keys in `model_id`'s own collation, so it works whatever the connection's collation is. The package reads that collation from `information_schema` once per process, so restart long-running workers after changing it. The package then reads your order 1,000 matches per query until it has `offset + perPage` of them: one query per 1,000 matches passed, and never a row that did not match. A page that starts past every match the index ranks for the query is empty and reads nothing from the model's table, with or without `orderBy()`. The subquery needs the index on the model's connection, the default connection, where the index tables live. A model on another connection is ordered over its top `max_candidates` matches by BM25 rank (at least one `bm25.candidate_chunk`), passed as a list of ids. Its deeper matches count in `total()` but are served on no page, and with string keys on SQL Server `max_candidates` should stay under about 2,000, because each id is one bound parameter. Under `orderBy()`, `_score` is normalised against the best-scoring row in the window up to the end of the page, so it is not comparable across pages; without `orderBy()` it is anchored at rank 1. A model that overrides `getSearchScore()` has its raw BM25 score passed through it before normalisation, and the first `max_candidates` matches are re-ranked by it. Deeper pages keep the BM25 order, just as LIKE pages past `max_candidates` keep the database order, so every match is on exactly one page. Every terminal (`get()`, `first()`, `paginate()`, `simplePaginate()`, `count()`) caps the term at `query.max_term_length`. An empty term throws `EmptySearchTermException` on every terminal, unless `allow_empty_search` is on.

> **Note:** `useIndex()` is an alias for `useInvertedIndex()`. The deprecated legacy `search_index` table from v1 is no longer used.

> **Primary keys:** Integer, UUID, ULID and other string primary keys up to 191 characters are supported (`model_id` is stored as a 191-character string).

### Column weights on the index (BM25F-lite)

`searchIn()` weights (and `$searchable['columns']` weights) now scale ranking on `useInvertedIndex()` too, not just the LIKE/Levenshtein paths:

```php
Product::search('watch')
    ->useInvertedIndex()
    ->searchIn(['title' => 10, 'description' => 1])
    ->get();
```

- Each column's term frequency is scaled by its weight and summed per document and term before BM25 saturation runs once (BM25F-lite) — heavier columns win ties and near-ties, but a 10:1 weight does not multiply the final score by 10.
- A weight of `0` removes that column from scoring entirely. Weights are integers `>= 1`: a fractional weight is truncated to an integer (`0.5` becomes `0`, i.e. removed).
- The list form `searchIn(['title'])` sets that column to weight **1** and leaves the model's other weights in place — pass explicit weights (`searchIn(['title' => 10, 'description' => 1])`) when you mean to re-rank.
- Hook models (`searchableText()`) are weighted by the hook's returned keys when a key matches a searchable column name; any other key weighs 1.
- Postings are stored per `(term, column)`, but the scorer sums them in SQL first: `bm25.max_postings_per_term` is one shared cap over the query's matched terms applied to `(document, term)` rows ordered by weighted frequency (highest first), so a document is never partially cut across its columns — raise the cap if your corpus reaches it.
- Requires `php artisan migrate` and `php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh` per model — rows indexed before this feature rank at weight 1 until rebuilt, and `php artisan fuzzy-search:status` lists them.

### Typo tolerance, as-you-type, synonyms and stop words on the index

The inverted index expands your query through its own term dictionary, so it no longer needs an exact token to match:

```php
User::search('jonh')->useInvertedIndex()->get();                 // finds "john" (typoTolerance() = 2 by default)
User::search('jonh')->useInvertedIndex()->typoTolerance(0)->get(); // exact terms only
User::search('joh')->useInvertedIndex()->asYouType()->get();      // last token is a prefix: john, johnny …
User::search('laptop')->useInvertedIndex()->withSynonyms(['laptop' => ['notebook']])->get();
User::search('the pro')->useInvertedIndex()->ignoreStopWords(['pro'])->get(); // added to the configured list for this query
```

- Each query term of at least `typo_tolerance.min_word_length` characters is expanded with up to `bm25.fuzzy.max_expansions` dictionary terms within `typoTolerance()` edits, closest first. With `bm25.fuzzy.damping` (default on) an expansion contributes `1 − distance / length` of what the exact term would, so it always counts for less — but it is not outranked automatically: BM25 weighs rarity (idf), so a rare expansion can still outscore a common exact term. `typo_tolerance.enabled = false` turns expansion off globally.
- Expansions are picked from the `bm25.fuzzy.candidate_pool` (default 500) most common dictionary terms of a similar length that this model has posted (the dictionary is shared by every indexed model, but another model's terms never fill the pool) — a term outside that window is **never** reached, however close it is. Rare surnames, SKUs and part numbers live in that tail, so raise the pool for such catalogs.
- `asYouType()` (or `$searchable['as_you_type' => true]`) expands the **last** token by prefix to terms this model has posted, capped at `bm25.prefix.max_expansions`.
- Synonyms score at full weight (they are alternatives, not typos). On the inverted index `ignoreStopWords()` **adds** its list to the configured locale list for that query — a term dropped at index time cannot match anyway, so a configured stop word cannot be restored, and `ignoreStopWords([])` cannot bring one back. On the LIKE path it still replaces the configured list.
- `highlight()` marks every term that matched, including expansions. `getDebugInfo()['index_terms']` lists the weighted terms that ran: the user's own words and their synonyms always, and a typo, prefix or as-you-type expansion only when it is posted under a column the model shows (an expansion only a hidden column holds still matches but is not listed).
- Index terms are at most 191 characters. A plain search cuts its term to `query.max_term_length` (128 by default) first, so a token longer than that is found through `asYouType()` (a prefix search), or once you raise `query.max_term_length` above its length. `suggest()` and `didYouMean()` never offer a word from a column the model hides; the typo and prefix expansions still match it, as the LIKE path does.
- The Scout engine keeps exact-term matching; use the builder for typo-tolerant index searches.
- Upgrading from v2.0: the dictionary gained a `term_length` column — run `php artisan migrate` (existing rows are backfilled).

### Artisan Commands

```bash
# Show index statistics (total docs, tokens, avg length per model) and list postings that predate column weighting
php artisan fuzzy-search:status

# Rebuild synchronously (good for < 50k rows); --fresh flushes the model's index first and asks no confirmation
php artisan fuzzy-search:rebuild "App\Models\User"
php artisan fuzzy-search:rebuild "App\Models\User" --fresh

# Rebuild asynchronously via queue (recommended for large tables)
php artisan fuzzy-search:rebuild "App\Models\User" --async
php artisan fuzzy-search:rebuild "App\Models\User" --fresh --async --queue=indexing

# Delete all index entries for a model (the same as fuzzy-search:clear; asks no confirmation)
php artisan fuzzy-search:flush "App\Models\User"

# Delete the index of every model (asks no confirmation)
php artisan fuzzy-search:clear --all
```

`flush`, `clear`, `clear --all` and `rebuild --fresh` delete index entries as soon as they run. None of them asks for confirmation, in production either, so that non-interactive deploy scripts keep working. Guard them in your own production scripts. A confirmation prompt is planned for v3.

`--async` needs Laravel's `job_batches` table (`php artisan make:queue-batches-table`; Laravel 10: `queue:batches-table`). Without it the command stops before it touches the index, `--fresh` included.

Run `fuzzy-search:flush`, `fuzzy-search:clear` and `rebuild --fresh` (which flushes first) while nothing is indexing any model: stop the queue workers that run `IndexModelJob`/`RebuildIndexJob` (a queued job indexes whatever `indexing.enabled` says) and keep requests from saving searchable models. Turning `indexing.enabled` off stops only the package's observer, not queued jobs or the Scout engine. A flush gives back the flushed model's share of each word's `doc_count`, then deletes every word no model's index uses any more, whichever model it came from. A write for the flushed model that commits during the flush can leave a word that other models share with a `doc_count` that is too high. That count only orders `didYouMean()`, `suggest()` and the typo and prefix expansions, not BM25 scores. `fuzzy-search:clear --all` followed by a rebuild of each model resets it. A write for another model that reuses a word the flush is deleting is not safe either. On MySQL/MariaDB the write keeps the word (it inserts it again if the flush deleted it first), but the two can deadlock (the write retries, and the flush can be run again). On PostgreSQL and SQL Server the flush can delete the word after the write commits, together with the write's new posting, so that row is not found by that word until it is indexed again. If something did index during a flush, rebuild the models it indexed.

Rebuilds load rows through the model's optional `searchIndexQuery()` hook (see *Searchable fields backed by accessors*), so relation-backed columns can be eager-loaded instead of queried once per row.

### BM25 Tuning

```php
// config/fuzzy-search.php
'bm25' => [
    'k1' => 1.5,   // Term-frequency saturation (1.2–2.0). Higher = more weight to repeated terms.
    'b'  => 0.75,  // Length normalisation (0–1). 0 = ignore doc length. 1 = full normalisation.
    'fuzzy' => [
        'candidate_pool' => 500,  // Dictionary terms (most common first) considered per query term for typo expansion.
        'max_expansions' => 5,    // Max dictionary terms added per query term within typoTolerance() edits.
        'damping'        => true, // An expansion contributes 1 - distance/length of what the exact term would.
    ],
    'prefix' => [
        'max_expansions' => 10,   // Max dictionary terms added by asYouType() for the last token's prefix.
    ],
],
```

### Observer Auto-Attach

Adding the `Searchable` trait automatically registers observers via `bootSearchable()`:

- **`SearchableIndexingObserver`** — listens to `saved` and `deleted` events and, once the model's transaction commits, queues an `IndexModelJob` (or runs it in-process with `indexing.async` off) to update the BM25 index. This is a no-op when `indexing.enabled` is `false`.
- **`SearchableObserver`** — listens to `saved` events and writes metaphone shadow columns if they exist. Safe when no shadow columns are configured — the observer silently exits.

No configuration is required for either observer until you enable those features.

#### Searchable fields backed by accessors

A searchable column does not have to be a real column. An accessor that reads a relation works too, but the observer cannot see it change, so declare the real columns that should trigger a reindex:

```php
use Illuminate\Database\Eloquent\Builder;

class Product extends Model
{
    use Searchable;

    protected array $searchable = [
        'columns'    => ['name' => 10, 'brand_name' => 5],
        'reindex_on' => ['brand_id'],   // real columns that invalidate brand_name
    ];

    public function getBrandNameAttribute(): ?string
    {
        return $this->brand?->name;
    }

    // Optional: the query fuzzy-search:rebuild loads rows through — eager-load here
    public function searchIndexQuery(Builder $query): Builder
    {
        return $query->with('brand');
    }
}
```

Without `reindex_on`, a model with an accessor-backed column is reindexed on **every** save (correct, but wasteful on hot paths such as stock updates). With it, only changes to the searchable columns or the listed triggers reindex. Indexing always reloads the row from the database first, so a relation that was already loaded on the instance before the change is never written to the index.

**Global scopes that depend on the request.** The indexer (`IndexModelJob`, `RebuildIndexJob` and `fuzzy-search:rebuild`) loads rows through the model's global scopes, and a queue worker or the CLI has no request and no authenticated user. A scope that reads either, such as a tenant resolved from `auth()`, can hide valid rows there: the job then **removes** a row that should stay indexed, and a rebuild skips it. For such a model, declare `searchIndexQuery()` and drop that scope, keeping `SoftDeletes`:

```php
public function searchIndexQuery(Builder $query): Builder
{
    return $query->withoutGlobalScope(TenantScope::class); // SoftDeletes still applies
}
```

Searches still apply the scope, and so do `suggest()` and `didYouMean()` (see "What scopes a suggestion" in the README).

Changing the *related* row (renaming the brand) does not reindex the products that reference it — handle that with an observer on the related model or a `fuzzy-search:rebuild`.

### Sync vs Async

| | `async = true` (default) | `async = false` |
| --- | --- | --- |
| **How it works** | Dispatches `IndexModelJob` to queue | Indexes in the same request, no queue |
| **Request latency** | Unaffected | +~10ms per save |
| **Requires queue worker** | Yes | No |
| **Best for** | Production apps | Tests, local dev, low-traffic apps |

For **tests**, set `indexing.async = false` so indexing happens synchronously:

```php
// In your test setUp
config(['fuzzy-search.indexing.enabled' => true, 'fuzzy-search.indexing.async' => false]);
```
