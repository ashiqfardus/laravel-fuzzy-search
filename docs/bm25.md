# The BM25 Inverted Index

[← Back to the README](../README.md)

## BM25 Inverted Index

For large tables (10k+ rows), the BM25 inverted index provides ranked, fast results without scanning the full table.

### How It Works

The indexing system has two parts:

**Part 1 — One-time initial build.** Run once after install (or after a schema change):

```bash
php artisan fuzzy-search:rebuild "App\Models\User" --fresh
```

**Part 2 — Automatic incremental updates.** Once `indexing.enabled` is `true` (it ships `false`; see [Production Setup](#production-setup)), every time a model is saved or deleted, the package dispatches a small queue job that re-indexes just that one row. No cron jobs or manual work needed.

The job is dispatched once the save's transaction commits (a rolled-back save indexes nothing). Writes for the same row wait for each other on the database, so an overlap can never count a row twice; an error in a synchronous index write is reported through your exception handler, not thrown from `save()`. Writes that fire no Eloquent events are not seen: `Model::query()->update()`, `insert()`, a query-builder `delete()`, `saveQuietly()`, `Model::withoutEvents()` and raw SQL. Re-index rows written this way with `fuzzy-search:rebuild`. A plain rebuild also removes the documents of rows such a write deleted or trashed, or that the model's `searchIndexQuery()` leaves out. A row moved out of a global scope keeps its document until `IndexModelJob::dispatch(Model::class, $id)` repairs it (the job removes a row that is gone or hidden) or a `rebuild --fresh`.

The flow when a record is saved:

```
User::create(['name' => 'John'])
  → Eloquent fires 'saved' event
  → once the transaction commits, SearchableIndexingObserver dispatches IndexModelJob to queue
  → queue worker claims the row's index entry, re-reads the row and indexes it as stored
  → 'john' is now in the index
```

The indexer indexes the row as it is stored at that moment, not the instance that was saved: whichever write commits last leaves the latest save indexed, and a row that is gone, soft-deleted or hidden by the model's global scopes leaves the index. Inside a transaction of yours on MySQL/MariaDB (Scout with `after_commit` off, `searchable()` or `IndexModelJob::dispatchSync()` in `DB::transaction()`), whose plain reads see the rows as its first read found them, it reads the row with a shared lock (`LOCK IN SHARE MODE`), held until your transaction ends, so a row another process deleted or saved since is indexed as it is now; for a row deleted since, that read also locks the gap where it was, so an insert there waits for your commit. The relations `searchIndexQuery()` eager loads are read without a lock (a shared read of them locked gaps in your own tables, so inserting a related row near them waited for your commit): `reindexRelated()` and a rebuild bring related text up to date. On a connection with a read/write split it reads the row, and the relations `searchIndexQuery()` eager loads (a `morphTo` one too), from the write connection, so a replica behind the commit cannot hand it the old row; a relation the `searchableText()` hook loads lazily is read as the connection reads, so eager-load it there. The Scout engine's `update()` reads the row as Scout's own jobs do instead (see [Scout Driver](integrations.md#scout-driver)). Under heavy contention a write that hits a deadlock is tried up to three times; one that loses all three is retried by the queue (`indexing.async`) or reported to your exception handler (sync). On PostgreSQL, parallel writes that add the same new words take the dictionary's rows in one order and do not deadlock; on SQL Server the writes to one index run one at a time (see [Production Setup](#production-setup)). On MySQL and MariaDB two writes can still cross on a word one of them read as new and the other as existing: the deadlock is retried, but with many parallel writers (16 batches at once, a `rebuild --async` or a queued `scout:import` on 16 workers) a few writes can lose all three attempts. The package's own jobs then try again (`indexing.job.tries`); Scout's queued import jobs run once, so run their queue workers with `--tries=3` (or set `scout.jobs.tries`, on a Scout version that reads it, as 11.x does). That holds for a write in a transaction of its own, which is how the package's observer writes: after the save's transaction commits. A write inside a transaction of yours (Scout with `scout.after_commit` off and no queue, or `searchable()` in `DB::transaction()`) is not retried, since Laravel does not retry a nested transaction: its deadlock is thrown (see [Production Setup](#production-setup)).

**Constraints are honoured on the index path.** Filters, `where()` constraints, joins, `having()`, `groupBy()`, unions and a `fromSub()` applied before the search, and global scopes (SoftDeletes included), apply before the page is cut. A selective filter fills its page from lower-ranked matches, and `paginate()` and `count()` totals reflect the constraints. The ranking is checked against the constraints by key, so a search reads rows bounded by what it ranked, however large the table. On every database but SQL Server, an integer key is checked in one query, the ranked ids inlined (about 1 ms per 1,000 ids). A string key on MySQL or MariaDB is checked 10,000 bound ids per query, except over a union, which they compare with a bound list one row at a time. On SQL Server, for a string key on PostgreSQL or SQLite, and for one over a union on MySQL or MariaDB, a ranking of at most `max(bm25.candidate_chunk, max_candidates)` ids (1,000 by default) is checked by key, `bm25.candidate_chunk` ids per query, and a longer one is read in one query through a subquery on `fuzzy_index_postings`; that query reads the key of every row the constraint accepts (on a SoftDeletes model, the whole table). A union is read as one derived table, in relevance order and under `orderBy()`, so every part of it must select the key (a union that selects none throws a `LogicException` saying so), and its own `orderBy()`, with no limit or offset of its own, orders the rows as an `orderBy()` on a query without a union does (before the builder's `orderBy()`); on SQL Server a union with a limit or offset of its own is not supported, as on the LIKE path. So a constrained search serves exactly the unconstrained search's rows that the constraint accepts, in the same order. On another connection than the index, where the subquery cannot run, those chunks check a ranking of any length (`bm25.candidate_chunk`, default 200):

```php
Product::search('watch')
    ->useInvertedIndex()
    ->filter('published', true)
    ->paginate(20);   // total = published matches only, pages never come back short

// Equivalent — filter()/filterIn() still work, but constraints can also be chained
// straight onto the builder (see [Chaining Eloquent](../README.md#chaining-eloquent)):
Product::search('watch')
    ->useInvertedIndex()
    ->where('published', true)
    ->paginate(20);
```

`_score` is scaled against the best-ranked row the query can see, so under constraints the top result scores `1` and a row the query hides never sets the scale. `_raw_score` is the unscaled BM25 value: its IDF and average document length come from the model's whole index, so on a shared multi-tenant index they count every tenant's rows. Leave `_raw_score` out of a response when one tenant must not learn anything about another's vocabulary.

### Database Tables

| Table | Purpose |
| --- | --- |
| `fuzzy_index_terms` | Term dictionary: unique terms (at most 191 characters) and how many documents, across every indexed model, hold each one. A search reads each model's own counts instead (`fuzzy_index_model_terms`). |
| `fuzzy_index_postings` | Postings: one row per `(term, model type, document, column)`, with the term's frequency in that column and the document's length. Its primary key starts with the term, so a word's postings are stored together and read as one range (the clustered index on MySQL, MariaDB and SQL Server; SQLite keeps the table `WITHOUT ROWID`; PostgreSQL `INCLUDE`s `frequency` and `doc_length` in the key's index). A secondary index `(model_type_id, model_id)` serves the writes and a flush. |
| `fuzzy_index_model_types` | The model types the postings are written under, as small ids. Rows are never deleted. |
| `fuzzy_index_columns` | The column names (and `searchableText()` keys) the postings are written under, one list for every model, as small ids (`''` marks postings written before column weighting). Rows are never deleted. |
| `fuzzy_index_model_terms` | Each model's own words: one row per `(model type, term)` it posts, with the word, its length and how many of the model's documents hold it, kept by every index write in its transaction. `didYouMean()`, `suggest()` and the typo and prefix expansions read a model's words here, most common by its own count first, and BM25's idf takes the model's document frequency from it. |
| `fuzzy_index_meta` | BM25 normalization: total docs + avg document length per model |
| `fuzzy_index_documents` | One row per indexed document, with its length: the writes claim it, and it feeds the meta totals; the ranking reads the length from the postings |

### Production Setup

**Step 1 — Run migrations:**

```bash
php artisan migrate
```

On PostgreSQL and SQLite the index tables can exist once per schema (or database file), whatever the table prefix: the package's index names do not carry the prefix, and an index name must be unique across the schema there, so a second install with another prefix fails to migrate. Use a schema (`search_path`) or a database per install. MySQL, MariaDB and SQL Server name indexes per table.

**Step 2 — Enable indexing in config:**

```php
// config/fuzzy-search.php
'indexing' => [
    'enabled'          => true,       // must be true or saves are never indexed
    'async'            => true,       // true = queued (recommended for production)
    'queue'            => 'indexing', // dedicated queue keeps indexing isolated
    'chunk_size'       => 500,
    'max_tokens_per_doc' => 5000,     // security cap: prevents index poisoning
],
```

**Step 3 — Declare searchable columns on your model:**

```php
use Ashiqfardus\LaravelFuzzySearch\Traits\Searchable;

class User extends Model
{
    use Searchable;

    protected array $searchable = [
        'columns' => [
            'name'  => 10,
            'email' => 5,
            'bio'   => 2,
        ],
    ];
}
```

**Step 4 — Build the initial index:**

```bash
# For small tables (< 50k rows)
php artisan fuzzy-search:rebuild "App\Models\User" --fresh

# For large tables (50k+ rows), dispatch batch queue jobs
php artisan fuzzy-search:rebuild "App\Models\User" --fresh --async --queue=indexing
```

`--async` needs Laravel's `job_batches` table: `php artisan make:queue-batches-table` (Laravel 10: `php artisan queue:batches-table`), then `php artisan migrate`.

**Step 5 — Start a queue worker:**

```bash
# Development
php artisan queue:work --queue=indexing,default

# Production (Supervisor)
```

Supervisor config (`/etc/supervisor/conf.d/fuzzy-search-worker.conf`):

```ini
[program:fuzzy-search-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/html/artisan queue:work database --queue=indexing,default --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
user=www-data
numprocs=2
redirect_stderr=true
stdout_logfile=/var/log/fuzzy-search-worker.log
```

**SQL Server: one index write at a time.** Each index write first takes an application lock on its index (`sp_getapplock`, named after the database and the table prefix, shared by every model type) and holds it until its transaction ends: parallel writers deadlocked on each other's locks until they lost all three attempts and left the index partial. So on SQL Server a second worker (`numprocs=2` above) adds no write throughput: each write, from its document claim (the re-read and tokenizing included) to its commit, waits for the one before it, and only the loading of the next rows runs alongside. The wait follows the connection's `LOCK_TIMEOUT` (none by default); a lock not granted throws a `RuntimeException` naming it. An index write inside a transaction of yours holds the lock until your transaction ends. A flush (`flush`, `clear`, `clear --all`, `rebuild --fresh`) takes it first too, so it waits for the write in flight and the next ones wait for it.

**Restoring the database under running workers** (a dump from another environment, a `db:wipe` and reload): restart them afterwards (`php artisan queue:restart`, `horizon:terminate` under Horizon, `octane:reload` under Octane). Each process remembers the ids of the index's model types and columns, which a restore can number differently, and a write would then file one model's words under another's. A test suite needs nothing: each test's application starts without them, and a truncate of the index tables, `migrate` or a schema load run in the process forgets them.

**Index writes inside your own transaction:** set `scout.after_commit` to `true`, or turn `scout.queue` on with a queue worker (on the `sync` queue connection Scout's job still runs inside the transaction), and index several models after the commit, or once for the collection (`$models->searchable()` is one write). The package's observer indexes after the save's transaction commits, but Scout with its defaults (`after_commit` off, no queue) indexes at once, inside the transaction, and so does a `searchable()` you call there. Every index write takes its dictionary words' locks in one order, but a transaction that holds two or more index writes (an order saved with its two searchable line items, say) keeps the first write's locks, on its words and its model's meta row, until it commits, and takes the next write's after them, out of that order: against other writers it can deadlock, on MySQL, MariaDB and PostgreSQL (on SQL Server the first write's index lock, held until your commit, keeps the other writers waiting instead). Laravel does not retry a nested transaction, so the write is not retried: `save()` or `searchable()` throws `Illuminate\Database\DeadlockException`, and your transaction rolls back. A transaction with one index write does not deadlock this way, nor, on MySQL/MariaDB, with a write of a neighbouring row: a re-index deletes and writes only the postings that change, each by its primary key. While a transaction with two or more index writes runs, though, the deadlock it causes can roll back either side: a transaction with one index write can then throw `DeadlockException` too, and now and then a write outside any transaction loses its three attempts (the queue retries it; with `indexing.async` off it is reported). Moving the transactions with two or more writes after the commit protects every writer. On MySQL/MariaDB its shared locks on the row (see [How It Works](#how-it-works)) make other writers of the row wait for your commit, and a transaction that indexes a row it has not updated, then updates it, can deadlock with another one indexing that row.

**SQL Server:** turn on `READ_COMMITTED_SNAPSHOT` for the database (`ALTER DATABASE … SET READ_COMMITTED_SNAPSHOT ON`, which waits until no other session uses the database: run it in a maintenance window, or add `WITH ROLLBACK IMMEDIATE`, which rolls back the open transactions of the others), or set `scout.after_commit` to `true` (Scout's default is `false`), which defers Scout's own save and delete hooks until the commit. The indexer re-reads a row after it claims the row's index entry. Under SQL Server's default locking read committed, that read waits on a row another transaction has updated but not committed. That transaction may be one that indexes before it commits: Scout with `after_commit` off and no queue, or `searchable()` or `IndexModelJob::dispatchSync()` inside `DB::transaction()`. Its index write in turn waits on the index write lock that write holds, so the two deadlock (error 1205, or the lock request chosen as the deadlock victim). Snapshot reads do not wait. An index write the package runs in a transaction of its own (the observer's, a queued `IndexModelJob`, a rebuild) yields in such a deadlock: it runs at a low deadlock priority, so SQL Server rolls it back and it is retried. One inside a transaction of yours keeps your priority, so there, under concurrent writes to the same rows, the victim can be that transaction, another of yours, or a plain read of those rows. `READ_COMMITTED_SNAPSHOT` is the recommended setting (Azure SQL Database has it on by default): with it, four concurrent writers indexing inside their transactions met no deadlock, and wrote faster. A `searchable()` you call yourself inside `DB::transaction()` still indexes at once, whatever `after_commit` says: call it after the commit, or turn on `READ_COMMITTED_SNAPSHOT`. If you run with `XACT_ABORT ON`, an index write that meets a new word (or a model's first document or meta row) that another write inserted at the same moment fails and is retried by the queue (or reported, when sync) instead of updating that row in place.

**PostgreSQL:** the package runs `ANALYZE` on its index tables (`fuzzy_index_postings`, `fuzzy_index_terms`, `fuzzy_index_documents`, the column and model type dictionaries `fuzzy_index_columns` and `fuzzy_index_model_types`, and each model's words, `fuzzy_index_model_terms`) at the end of `fuzzy-search:rebuild` (for `--async`, once the batch finishes, and again whenever a worker finishes the jobs queued so far before the next 300 are added; on the `sync` queue, where the jobs run inside the batch's own transaction, once that has committed). A synchronous `fuzzy-search:rebuild` runs `VACUUM (ANALYZE)` on the postings instead, outside any transaction and best-effort: it sets the visibility map that lets the ranking read the postings' primary key index alone (an `--async` rebuild leaves that to autovacuum, since its `finally()` runs inside the last job, under the job timeout). It also runs `ANALYZE` after the first index write that leaves the postings table past 16 pages (about 2,000 postings), or after the commit of the transaction that write ran in, and again whenever the postings table has more than doubled since it was last analyzed, until the statistics describe about 10,000 postings. Inside a transaction the check waits for the commit, since `ANALYZE` would hold its lock until then, and it runs once however many index writes the transaction held. The check is per `search_path`, so a worker that switches `search_path` per tenant (schema-per-tenant) checks each tenant's index tables. The `ANALYZE` and the check's catalog reads are best-effort: a failure, such as a lock timeout while autovacuum or another `ANALYZE` holds a table, is reported to your exception handler, not thrown. It cannot fail a save, a committed `DB::transaction()` or its later after-commit callbacks, or `fuzzy-search:rebuild`. Inside an open transaction it runs under a savepoint that any failure rolls back to (a lock timeout, a deadlock or a serialization failure alike), so the transaction stays usable. A connection lost there takes the transaction with it, so that failure is thrown, as the transaction's next statement would have thrown it; a `fuzzy-search:rebuild` run inside your own `DB::transaction()` then throws, and the transaction is gone. Past about 10,000 postings, autovacuum's own threshold (10% of the table) keeps them current. Below 16 pages of postings (about 2,000) the package analyzes nothing, a rebuild included: statistics taken on a handful of rows would make PostgreSQL plan a bulk index after them, inside one transaction, as a scan of the whole terms table for every posting, and a search over so few postings is fast whatever the plan. Autovacuum analyzes such small tables on its own. Without statistics, or with statistics taken on a much smaller table, the planner can run the postings subquery of a constrained or ordered index search as a nested loop over every posting for every row, which takes minutes at tens of thousands of rows. A database user that does not own the tables gets a warning and no statistics, so give the tables to that user, or analyze them as their owner. Two cases need an `ANALYZE` of your own, since the package cannot see them and analyzes only its index tables: a bulk import into a model's own table, and a `pg_restore` (which does not analyze). Run `ANALYZE` on the model's table before the first search after either, and on the index tables too after a `pg_restore`. An ordered index search reads the model's table, and until autovacuum analyzes it (within about a minute) an `orderBy()` search can be very slow: 80 to 90 s at 50k rows, against 0.3 s once the table was analyzed.

For **Laravel Horizon** (Redis):

```php
// config/horizon.php
'environments' => [
    'production' => [
        'supervisor-1' => [
            'connection' => 'redis',
            'queue'      => ['indexing', 'default'],
            'balance'    => 'auto',
            'processes'  => 4,
        ],
    ],
],
```

**Fetch mode:** the index and the persisted analytics need PDO's default object fetch mode. Under an app-wide array fetch mode (a `StatementPrepared` listener that sets `PDO::FETCH_ASSOC`), these throw `Attempt to read property … on array`: index searches (`useInvertedIndex()`) and `didYouMean()`; an index write or removal of a row the index already holds (`indexModel()`, `removeFromIndex()`, `indexBatch()`, `IndexModelJob`, so `fuzzy-search:rebuild` without `--fresh` and its `--async` jobs, and Scout's `searchable()`, import and delete); `fuzzy-search:status` once anything is indexed; every read of the search log (`SearchAnalytics`); and `fuzzy-search:analytics`. The package's observer reports its failed write instead of throwing, so the save succeeds and the index goes stale. The LIKE path, `suggest()` and `php artisan migrate` work there.

**Sizing:** the index takes about 1.5 GB per million rows of about 16 indexed words each on MySQL and 2.9 GB on PostgreSQL, several times the table, and it has to fit in the database's memory to stay fast. A search reads every posting of each word it matches before `bm25.max_postings_per_term` cuts the ranking, so a word in a few percent of the rows is the expensive search: on MySQL with a 4 GB buffer pool its first page took 0.81 s at 6M rows (three such words together 5.5 s). A `where()` does not shorten that read (the word's postings are read for the whole model before the `where()` and the cap apply), and `typoTolerance(0)` and Scout's exact terms skip only the typo expansion; for a selective filter over a common word, the LIKE path with an index on the filtered column is the fast path. More rebuild processes speed a large rebuild up (four gave 2.2× one on MySQL); `indexing.chunk_size` does not. See [Sizing the index](../README.md#sizing-the-index) for the measured limits.

### Usage

```php
// BM25 search — faster + better relevance on large tables
$users = User::search('john')->useInvertedIndex()->get();

// didYouMean() reads the term dictionary (no scan of your table)
$suggestions = User::search('jonh')->didYouMean(3);
```

`orderBy()` on the builder replaces the BM25 rank order. The page is then the first matches in that order, ties broken by the primary key ascending. The query keeps its select list, so you can order by a `withCount()` or `selectRaw()` alias. The ordered query reads only matching rows. When the ranking holds every match, it is restricted to their ids, so the rows it reads are bounded by the ranking, however large the table: an integer key's ids are inlined, on every database but SQL Server, and a string key's are bound on MySQL, MariaDB and SQLite while the query stays under the database's placeholder limit (65,535; SQLite's 32,766, or 999 before 3.32), except over a union on MySQL and MariaDB, which compare a bound list with a union's rows one by one (at 34,000 rows, 54 s where the subquery below takes 0.5 s). A ranking capped at `bm25.max_postings_per_term` (a word's read reached the cap: one row per document holding it, for a typed word, a prefix expansion or a synonym) is restricted through `fuzzy_index_postings` instead, which binds the model type and the query's terms, never a list of ids, and lets every match through, those past the cap too. A subquery restricts it, which reads the key of every row the query accepts (on a SoftDeletes model, the whole table; 40 to 100 ms at 1M rows on PostgreSQL and SQL Server, 0.7 to 4 s on MariaDB and MySQL). On MySQL and MariaDB, when the query has no constraint (no `where()` or `filter()`, join, `groupBy()`, `having()`, union, `fromSub()` or global scope but SoftDeletes) and the words' postings reach at most a tenth of the model's indexed rows, the matched terms' distinct ids are joined on the key instead, one key lookup per match, so the read follows the matches, not the table (at 1M rows, a word in 3 to 7% of them: 1.6 to 2.0 s before, 40 to 110 ms now on MySQL; 0.6 s and 30 to 75 ms on MariaDB). The join reads every matched posting, so under a constraint, and for a denser word, the subquery is the faster read (at 200k rows, a word in every row under a `where()` on an indexed tenant column of 100 rows: 2 ms, where the join took 3.3 s). The subquery also restricts a ranking of more than `bm25.candidate_chunk` matches (200 by default) on SQL Server, where a long id list compiles slowly or passes the 2,100-parameter limit (the subquery took 70 to 110 ms at 200k rows), and for a string key on PostgreSQL, where it measured as fast as a listed read. On MySQL and MariaDB it compares keys in `model_id`'s own collation, so it works whatever the connection's collation is, and the join looks a string key up in the key column's own collation; the package reads both collations from `information_schema` once per process, so restart long-running workers after changing either. On SQL Server it compares them in the database's default collation, `model_id`'s own, so a key column with a collation of its own works too. An aliased FROM (`from('users as u')`) or a subquery FROM (`fromSub(…, 'u')`) is read through its alias, and ties are broken by the alias's key (`u.id`). `total()` is the ordered query's count, and each page is one `LIMIT`/`OFFSET` read, however deep. A join that repeats a model (one-to-many) serves each model once, at its first row by the order, and `total()` counts models. When the order is on the model's own columns, the model's table is paged under the joined query's keys; when it is on a joined column, `ROW_NUMBER()` keeps each model's first row. Both take one read. A subquery FROM (`fromSub()`) that holds such a join, or a union whose parts share a row, is paged the same way, `ROW_NUMBER()` keeping each model's first row. Only an order on a select alias over such a join is found by reading the joined rows 1,000 at a time from the first, one query per 1,000 rows before the page; filter with `whereHas()` instead of a join to keep that order on one read. A page that starts past the last match is empty and reads no row, with or without `orderBy()`. Reading through the postings needs the index on the model's connection, the default connection, where the index tables live. A model on another connection is ordered over its top `max_candidates` matches by BM25 rank (at least one `bm25.candidate_chunk`), passed as a list of ids. Its deeper matches are neither served nor counted, and with string keys on SQL Server `max_candidates` should stay under about 2,000, because each id is one bound parameter. Under `orderBy()`, `_score` is normalised against the best-scoring row on the page, so it is not comparable across pages. A match past `bm25.max_postings_per_term` has no BM25 score, so its `_raw_score` and `_score` are 0. Without `orderBy()`, `_score` is anchored at the first match the query accepts, the same row on every page, and a page reads only its own rows, however deep. An indexed row deleted without a model event (see [BM25 Inverted Index](../README.md#bm25-inverted-index) on writes that fire none) leaves its page one row short, and lowers `_score` on every page, until it leaves the index: `fuzzy-search:rebuild --fresh`, or `IndexModelJob` for that row (a plain rebuild reads only the rows that exist). Meanwhile `first()` reads on to the next match, and `simplePaginate()` takes whether another page follows from the ranking, so the pages after it stay reachable (a page can come back empty: the last one, or with a scoring hook the first past the window it re-ranks). A model that overrides `getSearchScore()`, and a search with `customScore()` or `boostRecent()`, has each raw BM25 score passed through those hooks, in that order, before normalisation, and the first `max_candidates` matches are re-ranked by the result; every page then also reads those matches' rows. `_score` is then scaled against the best of them, the same row on every page and terminal, so the top result scores `1`, and a match past them scores no more than the last of them, however its hooks score it. Deeper pages keep the BM25 order, just as LIKE pages past `max_candidates` keep the database order, so every match is on exactly one page. Every terminal (`get()`, `first()`, `paginate()`, `simplePaginate()`, `count()`) caps the term at `query.max_term_length`. An empty term throws `EmptySearchTermException` on every terminal, unless `allow_empty_search` is on.

> **Note:** `useIndex()` is an alias for `useInvertedIndex()`. The deprecated legacy `search_index` table from v1 is no longer used.

> **Primary keys:** Integer, UUID, ULID and other string primary keys up to 191 characters are supported (`model_id` is stored as a 191-character string). A string key must be declared as one, `protected $keyType = 'string';` (`HasUuids` and `HasUlids` declare it): the indexer re-reads each row by its key, and under Eloquent's default `int` key type that read finds no row on SQLite, fails on PostgreSQL and SQL Server, and can read other rows on MySQL and MariaDB, which compare the key as a number. MySQL/MariaDB (`utf8mb4_0900_bin`, or `utf8mb4_nopad_bin` on MariaDB), PostgreSQL and SQLite compare keys byte-wise, trailing spaces included, so keys that differ only by case (`aBc` and `AbC`: sqids, hashids, base62) or by a trailing space are separate documents (MySQL before 8.0.17 has no such collation; its `utf8mb4_bin` ignores trailing spaces). An index that 2.0 built on MySQL/MariaDB merged them, and its counts drifted: rebuild such a model with `fuzzy-search:rebuild --fresh`, which restores its `total_docs`. A plain rebuild indexes both keys but leaves `total_docs` above the model's document count. On SQL Server `model_id` keeps the database's default collation, usually case-insensitive: two keys that differ only by case are one key there. A `fuzzy-search:rebuild` chunk holding both fails on the documents primary key (2627, or 8672 when one of them is already indexed) and the rebuild stops there: that chunk and every chunk after it stay unindexed (with `--async`, that chunk's job fails). Indexing them one at a time leaves only the last one findable. On SQL Server, give such a model keys that are unique regardless of case.

### Column weights on the index (BM25F-lite)

`searchIn()` weights (and `$searchable['columns']` weights) now scale ranking on `useInvertedIndex()` too, not just the LIKE/Levenshtein paths:

```php
Product::search('watch')
    ->useInvertedIndex()
    ->searchIn(['title' => 10, 'description' => 1])
    ->get();
```

- Each column's term frequency is scaled by its weight and summed per document and term before BM25 saturation runs once (BM25F-lite) — heavier columns win ties and near-ties, but a 10:1 weight does not multiply the final score by 10.
- A weight of `0` removes that column from the search entirely: its postings neither score nor match, and `count()` skips them. The LIKE and `extended()` searches leave it out too. Weights are integers `>= 1`: a fractional weight is truncated to an integer (`0.5` becomes `0`, i.e. removed).
- The list form `searchIn(['title'])` sets that column to weight **1** and leaves the model's other weights in place — pass explicit weights (`searchIn(['title' => 10, 'description' => 1])`) when you mean to re-rank.
- A builder whose columns leave out one the model searches (`searchOn($query, $term, ['name'])`, a plain query builder's `searchIn(['name'])` with `useInvertedIndex(Model::class)`) matches only its own columns on the index, as on the LIKE paths; postings written before column weighting (`''`) still match until you rebuild.
- `tokenize()->matchAll()` holds on the index too: a match holds each word, or one of its synonyms or typo and prefix expansions, in a column the search reads.
- Hook models (`searchableText()`) are weighted by the hook's returned keys when a key matches a searchable column name; any other key weighs 1.
- Postings are stored per `(term, column)`, but the scorer sums them in SQL first: `bm25.max_postings_per_term` caps each matched term on its own, applied to its `(document, term)` rows ordered by weighted frequency (highest first), so a document is never partially cut across its columns, and a common term never pushes a rarer term's matches out of the ranking; a term in no more of the model's documents than the cap is read whole. A search reads at most the cap's rows per term (terms × cap in all, typo and prefix expansions and synonyms included), and PHP keeps one score per document, not the rows — raise the cap if your corpus reaches it. In relevance order, results and their `total()`/`count()` cover the matches the capped ranking holds; `orderBy()` still serves and counts every match. The cap applies to the whole model before any `where()` or scope: a filtered relevance search serves only the filtered matches the capped ranking holds. Of `(document, term)` rows of equal weighted frequency the cap keeps those of the lowest `model_id` (as the database orders that column), so the capped ranking is the same on every request. Use `orderBy()`, or raise the cap, when a filter must see every match.
- Requires `php artisan migrate` and `php artisan fuzzy-search:rebuild "App\Models\YourModel"` per model (a plain rebuild replaces each row's postings, and can run while the app indexes) — rows indexed before this feature rank at weight 1 until rebuilt, and `php artisan fuzzy-search:status` lists them (add `--legacy` once the index holds more than 1,000,000 tokens).

### Typo tolerance, as-you-type, synonyms and stop words on the index

The inverted index expands your query through its own term dictionary, so it no longer needs an exact token to match:

```php
User::search('jonh')->useInvertedIndex()->get();                 // finds "john" (typoTolerance() defaults to typo_tolerance.max_distance, 2)
User::search('jonh')->useInvertedIndex()->typoTolerance(0)->get(); // exact terms only
User::search('joh')->useInvertedIndex()->asYouType()->get();      // last token is a prefix: john, johnny …
User::search('laptop')->useInvertedIndex()->withSynonyms(['laptop' => ['notebook']])->get();
User::search('the pro')->useInvertedIndex()->ignoreStopWords(['pro'])->get(); // added to the configured list for this query
```

- Each query term of at least `typo_tolerance.min_word_length` characters is expanded with up to `bm25.fuzzy.max_expansions` dictionary terms within `typoTolerance()` edits, closest first. With `bm25.fuzzy.damping` (default on) an expansion contributes `1 − distance / length` of what the exact term would, so it always counts for less. An expansion of a word the model's index holds is scored with that word's idf when its own is higher (a blended document frequency, as Lucene's fuzzy query scores): a word's misspellings are rare, and with their own idf the few misspelled rows of a common word ranked above every exact hit of it. With the damping a misspelled row now scores below an exact hit of the same frequency and length. An expansion of a word the index lacks (the user typed the misspelling) keeps its own idf, so the rarest close words still lead. Prefix (`asYouType()`) and synonym terms keep their own idf too. `typo_tolerance.enabled = false` turns expansion off, as it stops typo matches on every path (the `fuzzy` and `levenshtein` algorithms and `~` too), whatever `typoTolerance()` says.
- Expansions are picked from the `bm25.fuzzy.candidate_pool` (default 500) most common of this model's own terms of a similar length, by its own document count, equal counts newest word first (another model's terms never fill the pool, nor are they read) — a term outside that window is **never** reached, however close it is. Rare surnames, SKUs and part numbers live in that tail, so raise the pool for such catalogs. A word in more than half of the model's documents, or in more than `bm25.max_postings_per_term` of them, is never an expansion: it holds no signal for a misspelling, and the ranking read every one of its postings (`smith` expanded into `with`, in 999,967 of 1M products, and that read took 2.0 to 2.5 s). The words you type, prefix completions and synonyms match at any frequency.
- `asYouType()` (or `$searchable['as_you_type' => true]`) expands the **last** token by prefix to terms this model has posted, the most common by its own document count first, capped at `bm25.prefix.max_expansions`.
- Synonyms score at full weight (they are alternatives, not typos). On the inverted index `ignoreStopWords()` **adds** its list to the model's index stop-word list (the top-level `locale` key's, or `$searchable['locale']`'s) for that query — a term dropped at index time cannot match anyway, so a configured stop word cannot be restored, and `ignoreStopWords([])` cannot bring one back. On the LIKE path it still replaces the configured list.
- `highlight()` marks every term that matched, including expansions. `getDebugInfo()['index_terms']` lists the weighted terms that ran: the user's own words and their synonyms always, and a typo, prefix or as-you-type expansion only when it is posted under a column the model shows (an expansion only a hidden column holds still matches but is not listed).
- Index terms are at most 191 characters. A plain search cuts its term to `query.max_term_length` (128 by default) first, so a token longer than that is found through `asYouType()` (a prefix search), or once you raise `query.max_term_length` above its length. `suggest()` and `didYouMean()` never offer a word from a column the model hides, nor from a relation column `searchableText()` indexes under a dotted name declared in `$searchable['columns']` (`'author.email'`) when the related model hides that column or the model hides the relation; the typo and prefix expansions still match it, as the LIKE path does.
- The Scout engine keeps exact-term matching; use the builder for typo-tolerant index searches.
- Upgrading from v2.0: the dictionary gained a `term_length` column — run `php artisan migrate` (existing rows are backfilled).

### Artisan Commands

```bash
# Show index statistics (total docs, tokens, avg length per model) and list postings that predate column weighting
# (past 1,000,000 indexed tokens that check, which reads every posting, runs only with --legacy)
php artisan fuzzy-search:status
php artisan fuzzy-search:status --legacy

# Rebuild synchronously (good for < 50k rows); --fresh flushes the model's index first and asks no confirmation.
# Without --fresh, the documents of rows deleted, trashed or left out by searchIndexQuery() are removed after the walk
# (one keyed read of the table per 1,000 documents; with --async, in the batch's last job).
php artisan fuzzy-search:rebuild "App\Models\User"
php artisan fuzzy-search:rebuild "App\Models\User" --fresh

# Rebuild asynchronously via queue (recommended for large tables)
php artisan fuzzy-search:rebuild "App\Models\User" --async
php artisan fuzzy-search:rebuild "App\Models\User" --fresh --async --queue=indexing

# Delete all index entries for a model (the same as fuzzy-search:clear; asks no confirmation).
# A model you renamed or deleted is cleared by the class name its rows were indexed under.
php artisan fuzzy-search:flush "App\Models\User"

# Delete the index of every model (asks no confirmation)
php artisan fuzzy-search:clear --all
```

`flush`, `clear`, `clear --all` and `rebuild --fresh` delete index entries as soon as they run. None of them asks for confirmation, in production either, so that non-interactive deploy scripts keep working. Guard them in your own production scripts. A confirmation prompt is planned for v3.

`--async` needs Laravel's `job_batches` table (`php artisan make:queue-batches-table`; Laravel 10: `queue:batches-table`). Without it the command stops before it touches the index, `--fresh` included. The command queues the batch's jobs 300 at a time (the database queue inserts each 300 in one statement, under every database's bound-parameter limit), reading the keys a chunk at a time; if queuing fails part way, it exits 1, says how many jobs were queued and to run the rebuild again, which indexes every row.

Run `fuzzy-search:flush`, `fuzzy-search:clear` and `rebuild --fresh` (which flushes first) while nothing is indexing any model: stop the queue workers that run `IndexModelJob`/`RebuildIndexJob` (a queued job indexes whatever `indexing.enabled` says) and keep requests from saving searchable models. Turning `indexing.enabled` off stops only the package's observer, not queued jobs or the Scout engine. On PostgreSQL and SQL Server a flush holds index writes off itself: it waits for the ones in flight and makes new ones wait until it commits, so a write during it lands after it (on PostgreSQL searches go on). `clear --all` does so on every database (MariaDB from the moment it holds the tables). On PostgreSQL and MariaDB it truncates the postings, the documents and each model's words (on PostgreSQL all five index tables), so searches wait for it too, briefly, unless the tables stay busy (it never waits for a transaction that has read them) or the database user may not truncate; on SQL Server it truncates them behind its write lock. On MySQL it always deletes row by row, as the others do when they cannot truncate: on a large index that takes hours and fills the database's log, and the command says so. To empty a large MySQL index, truncate the tables yourself while nothing is indexing ([the upgrade guide](UPGRADE_v2.0_TO_v2.1.md) gives the statements, under A large index). A flush gives back the flushed model's share of each word's `doc_count`, then deletes every word no model's index uses any more, whichever model it came from. On MySQL and MariaDB a write for the flushed model that commits during the flush can leave a word that other models share with a wrong `doc_count`, too high or too low. No search reads that count: `didYouMean()`, `suggest()`, the typo and prefix expansions and BM25's document frequency read each model's own counts (`fuzzy_index_model_terms`) instead, which the flush deletes with the flushed model's postings. `fuzzy-search:clear --all` followed by a rebuild of each model resets it. A write for another model that reuses a word the flush is deleting is not safe either. On MySQL/MariaDB the write keeps the word (it inserts it again if the flush deleted it first), but the two can deadlock (the write retries, and the flush can be run again). If something did index during a flush, rebuild the models it indexed.

Rebuilds load rows through the model's optional `searchIndexQuery()` hook (see *Searchable fields backed by accessors*), so relation-backed columns can be eager-loaded instead of queried once per row.

### Single-table inheritance

A model's rows are indexed and searched under one model type, its `searchIndexType()`, which is the model's own class unless it says otherwise. Every save, delete, `IndexModelJob`, rebuild, `clear` and search uses it, and so does the Scout engine. Where a parent's query hydrates child instances (tightenco/parental and the like), a rebuild of the parent indexes each row under its own class: the parent's index search then finds only the rows hydrated as the parent (its LIKE search finds them all), and each child has an index of its own. Every other write named with the parent class does the same for each row it re-reads (the parent's `reindexRelated()`, `IndexModelJob::dispatch(User::class, $id)`, a child row saved through a parent instance). A save or delete files the row by its kind, the class the parent's query builds it as, whichever instance runs it: a type change, of the type column alone too, moves the row to its new class's index and out of the old one, a delete through a parent instance takes a child row out of the child's index, and a plain `fuzzy-search:rebuild` of the parent takes a row out of a kind it has left. A write whose class's query no longer reads the row (a child instance loaded before another request changed the row's kind, then saved or deleted; `IndexModelJob` named with the parent or a child after a query-builder write) reads it again through the parent without global scopes: the row goes to its kind's index, or, deleted, leaves every kind's. `fuzzy-search:rebuild --fresh` of the parent also takes a deleted row out of the other kinds' indexes. A subclass that is no kind of the hierarchy (its own query reads rows of the parent's kind as itself) keeps an index of its own, and a save through it writes the row's kind's index too. To index the hierarchy once, return the parent from each child:

```php
class Admin extends User
{
    use HasParent;

    public static function searchIndexType(): string
    {
        return User::class;
    }
}
```

Then run `php artisan fuzzy-search:rebuild "App\Models\User" --fresh`. The parent's index search finds every row of the hierarchy. A child's search (`Admin::search('ann')->useInvertedIndex()`, with its `count()` and `paginate()`, `didYouMean()`, and Scout's `Admin::search()`) reads the same index through the child's own global scope, so it finds only the child's rows. A save or delete of any class in the hierarchy writes that one index. A child's `suggest()`, `didYouMean()` and `getDebugInfo()['index_terms']` offer only the words of columns the child declares and shows and the parent shows too. The index does not record which class a word came from, so the parent's search judges every word on the parent: hide on the parent every column a child hides, or the parent's suggestions, and a sibling's that shows the column, can offer it. `fuzzy-search:rebuild` of a child rebuilds the parent's whole index, reading every row through the parent, and `fuzzy-search:clear` of a child clears it. A child that was indexed under its own class before has its old rows cleared by `fuzzy-search:clear "App\Models\Admin"` too. The method is static, and a Scout model without the package's trait can declare it the same way. It must return the class itself or a concrete Eloquent model the class extends on the same table and connection: anything else (a sibling, an abstract base class, a morph alias, a parent the class does not share a table with) throws a `LogicException` naming `searchIndexType()` when the model is indexed or searched, and a save reports it to your exception handler instead. Under an abstract base, leave each child indexed under its own class. The class a hook names resolves to its own index type, so in a deeper hierarchy (`SportsCar extends Car extends Vehicle`) each class can return its parent, and every row is indexed under the root's type. Each row is still tokenized with its own class's pipeline (`tokenizer`, `stemmer`, `stemmer_language`, `locale` in `$searchable`), and a search with the class it runs on: keep those keys on the parent, where the children inherit them.

### BM25 Tuning

```php
// config/fuzzy-search.php
'bm25' => [
    'k1' => 1.5,   // Term-frequency saturation (1.2–2.0). Higher = more weight to repeated terms.
    'b'  => 0.75,  // Length normalisation (0–1). 0 = ignore doc length. 1 = full normalisation.
    'fuzzy' => [
        'candidate_pool' => 500,  // The model's own terms (most common first, by its own document count) considered per query term for typo expansion.
        'max_expansions' => 5,    // Max dictionary terms added per query term within typoTolerance() edits.
        'damping'        => true, // An expansion contributes 1 - distance/length of what the exact term would.
    ],
    'prefix' => [
        'max_expansions' => 10,   // Max dictionary terms added by asYouType() for the last token's prefix.
    ],
],
```

### Observer Auto-Attach

Adding the `Searchable` trait automatically registers observers via `bootSearchable()`:

- **`SearchableIndexingObserver`** — listens to `saved` and `deleted` events and, once the model's transaction commits, queues an `IndexModelJob` (or runs it in-process with `indexing.async` off) to update the BM25 index. This is a no-op when `indexing.enabled` is `false`.
- **`SearchableObserver`** — listens to `saved` events and writes metaphone shadow columns if they exist. Safe when no shadow columns are configured — the observer silently exits.

No configuration is required for either observer until you enable those features.

#### Searchable fields backed by accessors

A searchable column does not have to be a real column. An accessor that reads a relation works too, but the observer cannot see it change, so declare the real columns that should trigger a reindex:

```php
use Illuminate\Database\Eloquent\Builder;

class Product extends Model
{
    use Searchable;

    protected array $searchable = [
        'columns'    => ['name' => 10, 'brand_name' => 5],
        'reindex_on' => ['brand_id'],   // real columns that invalidate brand_name
    ];

    public function getBrandNameAttribute(): ?string
    {
        return $this->brand?->name;
    }

    // Optional: the query fuzzy-search:rebuild loads rows through — eager-load here
    public function searchIndexQuery(Builder $query): Builder
    {
        return $query->with('brand');
    }
}
```

Without `reindex_on`, a model with an accessor-backed column is reindexed on **every** save (correct, but wasteful on hot paths such as stock updates). With it, only changes to the searchable columns or the listed triggers reindex. Indexing always reloads the row from the database first, so a relation that was already loaded on the instance before the change is never written to the index.

**Global scopes that depend on the request.** The indexer (`IndexModelJob`, `RebuildIndexJob` and `fuzzy-search:rebuild`) loads rows through the model's global scopes, and a queue worker or the CLI has no request and no authenticated user. A scope that reads either, such as a tenant resolved from `auth()`, can hide valid rows there: the job then **removes** a row that should stay indexed, and a rebuild skips it. For such a model, declare `searchIndexQuery()` and drop that scope, keeping `SoftDeletes`:

```php
public function searchIndexQuery(Builder $query): Builder
{
    return $query->withoutGlobalScope(TenantScope::class); // SoftDeletes still applies
}
```

Searches still apply the scope, and so do `suggest()` and `didYouMean()` (see "What scopes a suggestion" in the README).

Changing the *related* row (renaming the brand) does not reindex the products that reference it — handle that with an observer on the related model or a `fuzzy-search:rebuild`.

### Sync vs Async

| | `async = true` (default) | `async = false` |
| --- | --- | --- |
| **How it works** | Dispatches `IndexModelJob` to queue | Indexes in the same request, no queue |
| **Request latency** | Unaffected | +~10ms per save |
| **Requires queue worker** | Yes | No |
| **Best for** | Production apps | Tests, local dev, low-traffic apps |

For **tests**, set `indexing.async = false` so indexing happens synchronously:

```php
// In your test setUp
config(['fuzzy-search.indexing.enabled' => true, 'fuzzy-search.indexing.async' => false]);
```
