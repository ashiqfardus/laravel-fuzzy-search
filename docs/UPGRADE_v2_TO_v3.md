# Upgrading from v2 to v3

3.0 is a major release. It breaks code and configs written for 2.0: some calls now throw, return other rows or cache, a published 2.0 `config/fuzzy-search.php` takes effect for keys 2.0 ignored, and the migrations rewrite the index tables. Read this guide before you change your constraint to `^3.0` (a `^2.0` constraint never installs 3.0). It covers every behaviour change that can affect an existing v2.0 install.

## Upgrade checklist

1. Read [Behaviour changes](#behaviour-changes) and re-run your search tests: some calls now return other rows, throw, or cache. If you published `config/fuzzy-search.php` under 2.0, compare it with the new file: 2.0 ignored several of its blocks and 3.0 reads them ([Config keys that now take effect](#config-keys-that-now-take-effect)). Its `scoring` block (`prefix_match` 50, `contains` 25, `fuzzy_match` 10) now scores LIKE results, where a fresh install scores 80, 60 and 50: delete the block to take 3.0's defaults, or keep it on purpose.
2. Plan the window. Have free disk for a second copy of `fuzzy_index_postings` (and binary-log and replica headroom) before you migrate: on MySQL and MariaDB the `model_id` widening copies the postings and documents tables, and the compact migration builds a second postings table beside the first. On MySQL and MariaDB the migrations take a while on a large index: from 2.0.x, the whole upgrade from 2.0.1 took 4 m 33 s at 1M rows on MySQL (RC3 7c96ec9, migrations unchanged in the release), the compact postings migration alone about 22 minutes for 6M rows (67be9e1, before its later fixes) and the words backfill about 3 more (81bedf8), and one earlier migration (the `model_id` widening) copies the postings table first. Index searches fail until they finish: migrate under `php artisan down`, or empty the index and rebuild instead ("A large index", under [Inverted index (BM25)](#inverted-index-bm25)). On PostgreSQL and SQL Server 2.0.x could not write the index ([Database fixes you get for free](#database-fixes-you-get-for-free)), so the migrations find it empty and take seconds; build each model's index once afterwards (step 7).
3. Stop the queue workers that index and keep saves of searchable models off, install 3.0 with `composer require ashiqfardus/laravel-fuzzy-search:^3.0` (a `^2.0` constraint never installs it), then run `php artisan migrate`. A lock wait timeout (1205) during it means something still writes the index: stop it and run `php artisan migrate` again, which goes on where it stopped (the migration that stopped runs again; the postings copy and the model terms backfill go on after their last committed range). On SQL Server, an index write that fails with error 8622 during or after an interrupted migrate means the compact postings migration has not finished: stop the writers and run `php artisan migrate` again.
4. While they are still stopped, rebuild with `--fresh` each model a migration's warning names, and each model a section below sends to `--fresh`: `php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh`. It flushes the model's index first, so nothing may be indexing.
5. SQL Server: while the workers are still stopped, turn on `READ_COMMITTED_SNAPSHOT`, or set `scout.after_commit` to `true` (see [Inverted index (BM25)](#inverted-index-bm25)). The `ALTER DATABASE` waits for every other session to leave, so it can hang once the workers are back.
6. Then restart the queue workers and Octane, and let saves through (`php artisan queue:restart`, `horizon:terminate` under Horizon, `octane:reload` under Octane). Keep your queue connection's `retry_after` above `fuzzy-search.indexing.job.timeout` (120 seconds by default; Laravel's default `retry_after` is 90), or a long index job is reserved again by a second worker while the first still runs it and does its work twice.
7. Rebuild every other indexed model once, for weighted BM25 ranking: `php artisan fuzzy-search:rebuild "App\Models\YourModel"`. A plain rebuild re-indexes each row in place, replacing its old postings, and a save of the same row waits for it, so it runs with the workers and saves back on. On PostgreSQL and SQL Server it builds the index 2.0.x could not write.

## Behaviour changes

Every change below can alter what an existing call returns, throws, caches or writes. Most need no
code change; where one does, the bullet says what to do. The sections after this one hold the
details for config, pagination, relationship search, the extended syntax, the inverted index,
analytics, `suggest()` and the tokenizers.

### Search results

- **An `orWhere()` no longer escapes the search.** `search($term)->where(A)->orWhere(B)` now reads `(A or B) and <search>` on every path; 2.0 read `A or (B and <search>)` on the LIKE and extended paths, so every row of `A` came back whatever the term, and a `filter()` after the `orWhere()` held for `B` alone. Grouping your own conditions in a closure, `where(fn ($q) => $q->where(A)->orWhere(B))`, was always the way to get the new reading, and still is; such queries, and queries without an `or`, compile as before. If you relied on the old reading (every row of `A`, plus the rows of `B` that match), run two queries. A Scout `query()` callback's `orWhere()` is grouped the same way, so the builder's `where()`s hold for all of it.
- **Accented terms also search their accent-free form, and the typed form is kept.** Under the shipped `unicode.accent_insensitive => true`, 2.0 replaced "Müller" with "Muller". 3.0 searches both, so rows that spell the accent ("Zoë Müller") are found as well as those that don't. A row found only through the folded form ranks and highlights as a match of it. ASCII terms are unaffected: their SQL is byte-identical. An accented stop word (`für`, `à`, `être`) is now dropped as listed, because stop words are matched against the typed word. Folding the term never folds the column: an unaccented `cafe` finds `Café` as a substring match only under an accent-insensitive collation (MySQL/MariaDB) or through PostgreSQL's `unaccent()` below.
- **An accented term and its accent-free form count once for relevance.** A row scores the better of the two, never their sum, and in an `extended()` query a leaf and its folded form are one leaf; with folding off, `müller | muller` are two terms and add up. Unaccented terms score as in 2.0.
- **PostgreSQL: `unaccent()` needs an explicit opt-in.** With `use_native_functions=true`, the global `unicode.accent_insensitive` key no longer turns every search into `unaccent(col) ILIKE unaccent(?)`. Your chosen algorithm (pg_trgm `similarity()`, `SOUNDEX()`, …) runs again. To fold the column too, opt in explicitly: `->accentInsensitive()`, `$searchable['accent_insensitive' => true]`, or a preset. The `unaccent()` alternative is then ORed beside the algorithm. That opt-in requires the extension (`CREATE EXTENSION IF NOT EXISTS unaccent;`); without it such a search fails with `function unaccent(…) does not exist`.
- **`similar_text` returns far fewer rows on long columns.** `similar_text.min_percentage` (default `70`) is now enforced. A match contains the term, so its `similar_text()` percentage is `200·t / (t + v)`, and at 70% a value may be at most about 1.86 times the term's length. "john" still finds "John" and "Johnny" but no longer "John Doe" or "Bob Johnson". Lengths are counted in characters on every database. With `tokenize()`, the whole search term's length sets the bound for every token, so "john doe" still finds "John Doe". Set `similar_text.min_percentage` to `0` (or pass the per-call `min_percentage` option as `0`, or `fuzzySimilar($term, $columns, 0)`) to get 2.0's results back.
- **Auto-detected columns are text columns only.** A zero-config model no longer searches numeric, boolean or date columns picked from `$fillable` or as the first column, or a PostgreSQL enum. On PostgreSQL those searches failed, and elsewhere they matched digits. JSON and UUID columns are skipped where the database has a JSON or UUID type (JSON: MySQL, PostgreSQL; UUID: PostgreSQL, SQL Server, MariaDB's native `uuid`) and still detected where they are stored as text. A column the model casts to a JSON type (`array`, `json`, `object`, `collection`, `AsArrayObject`, `AsCollection`, or an `encrypted:` form of them) is never detected, on any database; on SQLite, MariaDB and SQL Server, cast a JSON column or declare `$searchable['columns']` to keep it out. If you relied on an auto-detected non-text column (for example an integer `code`), declare it in `$searchable['columns']`.
- **`orderBy()` on the builder now sticks.** It replaces the relevance order on every path; before, PHP rescoring re-sorted by `_score` on the LIKE path, and the extended and index paths ignored it. If you called `orderBy()` only to shape the candidate window, order the underlying query instead: `->query(fn ($q) => $q->orderBy('id'))`. `stableRanking()` now also applies on the `extended()` path. On `useInvertedIndex()` the ordered query reads only matching rows, through the index's postings; that needs the index on the model's connection. A model on another connection is ordered over its top `max_candidates` matches (at least `bm25.candidate_chunk`, 200 by default) by BM25 rank, and its deeper matches are neither served nor counted (see [the BM25 guide](bm25.md#usage)).
- **Multi-term `extended()` queries score each leaf term on its own**, adding the leaf scores, instead of scoring against all the terms joined into one string: `_raw_score` for those queries changes, and a row that matches more of the query ranks higher. Single-term queries are unchanged. Many-term queries give the similarity floor only to leaf terms within a 255-character total; later terms rank by exact, prefix or contains match alone.
- **A `getSearchScore()` override now runs.** 2.0 never called it, although the README's model example overrode it. A model that overrides it (such as the example's `is_featured` ×1.5 boost) now has each row's score passed through it before normalisation on the LIKE, extended and index paths and in the Scout engine (on the index path and in the engine, the first `max_candidates` matches), so its results rank differently. Remove the override to keep 2.0's ranking.
- **PostgreSQL with `use_native_functions`: `levenshtein` runs its pattern set.** 2.0 ran pg_trgm's `similarity()` there, which found no one-edit typo of a short word and no name inside a longer value; the pattern set finds both, so such searches return more rows. The flag still switches trigram, soundex and `unaccent()`.
- **Stop words match in any letter case.** `ignoreStopWords()` used to lower A–Z only, so a capitalised non-ASCII stop word ("Не", "À") and a list entry written with capitals stayed in the term on the LIKE path. They are dropped now, as on the index path, so such queries find more rows.
- **`customScore()` and `boostRecent()` now rank `useInvertedIndex()` results.** 2.0 applied them on the LIKE and extended paths only, and the index path ignored them. They now apply to the BM25 raw score as well, after `getSearchScore()`, and re-rank the first `max_candidates` matches, so an index search that sets either returns its rows in a different order, and every page reads those matches' rows. Remove the call to keep 2.0's order.
- **`distinct()` reads in key order on the LIKE path.** `search($term)->distinct()` threw in relevance order on PostgreSQL and SQL Server, and on MySQL when the select left out a searched column or the key. Under `distinct()` the search now adds no relevance `ORDER BY`; with no order of yours it reads the rows by the key when the select holds it, else by the columns it selects (PostgreSQL's `distinct('col')` by its own columns first), so its pages hold each match once on every database. PHP rescoring ranks the first `max_candidates` rows of that order. So past that many matches (1,000 by default) the best rows can be left out, where 2.0 ranked them in SQL on MySQL, MariaDB and SQLite. To rank or order every match, add an `orderBy()`, or drop `distinct()` (a join that repeats rows can be filtered with `whereHas()` instead).
- **Very long queries match fewer typo variants.** One search now binds at most 2,000 values of its own, on every database; 2.0 had no bound, and failed on SQL Server past 2,100. A query whose words, `extended()` leaves, accent-free forms and synonyms, times its columns, would need more LIKE patterns than that gets an equal share per word and column, always including the plain contains pattern, so it can find fewer typo matches than 2.0 did on the other databases. Queries within the budget are unchanged. Your own `where()` and `filter()` values are not counted. The multi-column helpers (`whereFuzzyMultiple()`, `fuzzySearch()`, the `Fuzzy` scopes, `tableSearch()`) share the budget across their columns too, so a long term on many columns can match fewer typo variants per column.
- **The `synonyms` config key is read.** 2.0 ignored it. If your published config lists synonyms, every `SearchBuilder` search now uses them (not `extended()`/`searchBoolean()` queries, the Scout engine, `FuzzySearch::on()` or the query-builder macros), merged under a model's `$searchable['synonyms']` and a query's `withSynonyms()`. Empty the key to keep 2.0's results.
- **A `!` negation keeps rows with NULL searchable columns** — such queries can return more rows than before.
- **PHP rescoring reads at most 255 characters** of a column value (and of a term) for its similarity and Levenshtein floor; exact, prefix and contains tiers still read the whole value.
- **`_highlighted` and `_matches` drop hidden columns** (`$hidden`, or outside `$visible`), on related models too, and `FuzzySearchResource` applies the row's current rule. `debugScore()`'s `_debug` leaves them out too, and `suggest()` never offers a word from one (see [`suggest()`](#suggest-on-an-indexed-model-now-completes-from-the-dictionary)).
- **The query macros and `Fuzzy` scopes cap the term at `query.max_term_length`** (default 128 characters), as `search()` always did. A longer term is truncated, not rejected. `fuzzyLevenshtein($term, $columns, 0)` now means exact containment; it used to run with the configured distance.
- **`?page` is read as a whole number of at least 1 on every paginator.** `?page=0` or `?page=-3` is page 1 instead of the wrong rows, and `?page=abc`, `?page[]=1` or a page past the integer range no longer throws a `TypeError` on the index path. `page(0)`, a negative `page()` and `skip(-n)` serve the first rows instead of the last.
- **A backslash in a search term is literal on MySQL, MariaDB and PostgreSQL.** 2.0 passed it to LIKE, which read it as an escape, so `back\slash` matched `backslash` and not itself. 3.0 escapes it on PostgreSQL; on MySQL and MariaDB every LIKE now carries `ESCAPE '!'`, under which a backslash is an ordinary character (and which, unlike their backslash default, still works under the `NO_BACKSLASH_ESCAPES` SQL mode). SQLite and SQL Server always treated it as literal.
- **Paginated BM25 `_score` now shares one scale across pages.** `_score` on a BM25 result is
  normalised against the best-ranked row the query can see — the same row on every page — not the
  page's own maximum, so page 2's top row is no longer always `1.0`. Under a `where()`, a join, a
  scope or `filter()`, that is the best match the query lets through, so the top result scores
  `1.0` (v2.0's `get()` scaled against the best match in the whole index, other tenants' included). The LIKE and extended paths changed too: `paginate()`
  now normalises `_score` across the whole `max_candidates` candidate window instead of within
  the current page (v2.0 behaviour); pages whose offset falls beyond that window still normalise
  within the page, same as before.
- **BM25 now honours your constraints before cutting the page.** `filter()`/`filterIn()`,
  `where()` constraints, and global scopes are applied *before* the ranking is cut to the
  requested page, instead of after. Selective filters no longer return short or empty pages, and
  `paginate()` totals now count only matching rows — if you were relying on the old (wrong)
  totals, expect them to change.
- **`fallback()` actually runs now.** Previously the fallback algorithms you registered were
  stored but never executed; if the primary search returned no rows, that was the end of it. Now
  each fallback runs in order until one matches. A fallback runs only when the primary matches nothing at all; a `simplePaginate()` or `skip()` page past the primary's matches stays empty.
- **Case-insensitive scoring and highlighting now cover every script.** They folded ASCII
  only, so a lower-case Cyrillic, Greek or accented term scored an upper-case value as a fuzzy
  near-miss and highlighted nothing. Such results now rank as exact/prefix/contains matches and
  are highlighted, so the order of non-ASCII results can change. ASCII-only text scores and
  highlights exactly as before; `_matches` indices are still byte offsets.
- **Rows MySQL/MariaDB match accent-insensitively now rank and highlight as matches.** Under an
  accent-insensitive connection collation (Laravel's `utf8mb4_unicode_ci`), `jose` returned
  `José Ramírez` as a near miss with no tag; it now ranks as the prefix match it is and is
  highlighted, so the order of such results can change. The same holds on PostgreSQL with
  `accentInsensitive()` and unaccent.
- **`min_search_length` now applies to every search, not only `get()`.** A plain term shorter
  than `min_search_length` characters (default 2) now matches nothing on `paginate()` (an empty
  page, total 0), `count()` (0), `getFacets()`, `FuzzySearch::on()`, the Scout engine and
  `FederatedSearch` models without the `Searchable` trait, as it always did on `get()`,
  `simplePaginate()` and `Searchable` models in `FederatedSearch`, and fires no
  `FuzzySearchExecuted`. In v2.0 `User::search('j')->paginate()` returned every row (the fuzzy
  patterns for a one-letter term match everything) while `->get()` returned nothing. Set
  `min_search_length` to `1` to search one-character terms again; the inverted index and the
  Scout engine still never match them, because they do not index one-character tokens.
  `extended()`/`searchBoolean()` queries, the `whereFuzzy`-style macros, the `Fuzzy` scopes and
  `tableSearch()` are unaffected.
- **A term made only of stop words matches nothing.** With `ignoreStopWords()`, `search('the')`
  applied no condition on the LIKE path and returned every row (the index path returned none); it
  now returns no rows and a total of 0 on both. An `extended()` query drops no stop words, so it is unchanged.
- **A search on a model with no searchable column now returns nothing instead of every row.**
  When a model declares no `$searchable['columns']`, auto-detection finds none (every text column
  hidden, say) and `searchIn()` is not called, `search()`, `searchOn()`, the `searchFuzzy()` scope
  and `useInvertedIndex()` added no condition and returned every row. They now match nothing, like
  a term below `min_search_length`: an empty collection or `null`, an empty page with a total of 0,
  a count of 0, empty facets, no `FuzzySearchExecuted` and no cache entry. Such a model contributes
  nothing to `FederatedSearch`, and `FuzzySearch::tableSearch()` matches nothing for it. `FuzzySearch::on($items)->search('term')` without `searchIn()` matches nothing too — it returned every item — and an empty term throws `EmptySearchTermException` unless `allow_empty_search` is on (see [Exceptions](#exceptions)). A `FederatedSearch` model without the `Searchable` trait, searched without `searchIn()`, is searched only on its declared columns (see the federated bullets below) or else on whichever of the guessed `name` and `title` columns its table has; with none of these it contributes nothing, where it used to throw (and on SQLite a term such as `name` matched every row). A
  `SearchBuilder` on a plain query builder without `searchIn()` matches nothing too, unless
  `useInvertedIndex(Model::class)` searches that model's index; a model with a `searchableText()`
  hook still searches on `useInvertedIndex()`. `getFacets()` always runs on the LIKE path, so
  without `searchIn()` those two index searches return empty facets while `get()` returns the
  index's matches. A model whose table cannot be read (a `$table` typo, a table not migrated yet)
  is not treated as having no column: the query runs and its database error surfaces. On
  `useInvertedIndex()` the table is read only when the index has matches, so an empty index
  still returns nothing without an error.
  `extended()`/`searchBoolean()` still throw `SearchableColumnsNotFoundException`, and the
  `whereFuzzy`-style macros take their columns explicitly. Declare `$searchable['columns']` to
  search such a model.
- **Invalid UTF-8 bytes are dropped from search terms.** `?q=jo%C3hn` now searches `john` on
  every database instead of erroring on PostgreSQL and SQL Server (and searching the raw bytes on
  SQLite and MySQL); the event and the analytics log record the cleaned term. A term made only of
  invalid bytes (`?q=%FF`) matches nothing on `search()`, `FederatedSearch` and `FuzzySearch::on()`:
  no rows, a total of 0, and no `EmptySearchTermException`. The query-builder helpers (the
  `whereFuzzy`-style macros, the `Fuzzy` scopes and `tableSearch()`) treat it as `''`.
- **A `SearchBuilder` is reusable.** Terminal calls compile onto a clone and no longer add the search's conditions to your base query, so `first()` followed by `get()` returns every match (it returned one row), and `suggest()` on a builder that already ran `get()` is no longer narrowed by that search.
- **`paginate()` ranks across up to `max_candidates` rows before slicing** (2.0 ranked within the page), and works with `extended()`/`searchBoolean()`.
- **`typoTolerance(0)` and `typoTolerance(1)` now apply to the default `fuzzy` algorithm**, which generated every typo pattern whatever the level, so those searches match fewer rows.
- **`typo_tolerance.enabled = false` now also stops typo matches on the `fuzzy` and `levenshtein` algorithms**, and in the `whereFuzzy`-style macros and the `Fuzzy` scopes. It used to turn off only the inverted index's typo expansion and `extended()`'s `~`. With it off, every search matches the term itself, whatever `typoTolerance()`, `$searchable['typo_tolerance']` or `levenshtein.max_distance` say, so those searches return fewer rows. Two smaller changes come with it, and neither shows at the shipped values: `typo_tolerance.max_distance` is now the default distance on the inverted index and `~` for every search (a model that declared `$searchable` without `typo_tolerance` used 2 there), and a zero-config model searched with `levenshtein` reads `levenshtein.max_distance`, as a declared model does (it read `typo_tolerance.max_distance`).
- **`search('0')` is a real search** for a one-character term. It threw `EmptySearchTermException` from `get()` and listed every row from `paginate()`/`count()`; at the default `min_search_length` of 2 it now matches nothing.
- **`min_search_length` and `query.max_term_length` count characters, not bytes**, so a one-character multibyte term is below the default minimum of 2, and a long non-Latin term keeps more of its characters.
- **The `searchFuzzy()` scope weighs the configured columns** with their `$searchable['columns']` weights (it weighed every column 1), so its ranking changes, and list-form columns no longer throw.
- **On a connection with a table prefix, write a qualified column's table unprefixed** in `orderByFuzzy()` and the other raw-SQL paths: the prefix is now added for you, so `orderByFuzzy('pre_users.name', …)`, which happened to work before, now names `pre_pre_users`.
- **`_highlighted` escapes every column** — see [below](#_highlighted-is-now-escaped-for-every-column).
- **`paginate()` and `simplePaginate()` clamp `perPage`** to between 1 and `max_candidates` — see [page sizes](#paginate-page-sizes).
- **`~`, `field:` and `!` are read differently by `extended()`** — see [Extended syntax](#extended-syntax--and-field-are-operators-now).
- **`suggest()` on an indexed model completes from the dictionary** — see [below](#suggest-on-an-indexed-model-now-completes-from-the-dictionary).
- **`using('trigram')` returns fewer rows, except on PostgreSQL with `use_native_functions` on.** The LIKE fallback no longer builds one- and two-character patterns from the padded ends of the term, which matched almost every row (`xyzq` found every user whose email holds an `x`). A gram shorter than three characters is dropped unless the term itself is shorter. Rows that share a three-character run with the term are still found. A typo that leaves no three-character run in common with the word (`jhon` for `John`) is no longer matched by the fallback; use `fuzzy` or `levenshtein` for typos in short words.
- **`using('levenshtein')` returns fewer rows for a short term.** A term shorter than `typo_tolerance.min_word_length` (4 by default) matches only the rows that contain it, as with `fuzzy`, and no typo pattern keeps fewer than three characters of the term. `jo` used to find most of a table, and `john` found `Monica Geller` through the pairs `on` and `hn`. A one-edit typo of a word of four letters or more is still found.
- **An empty or NULL column no longer earns the typo floor.** With `typoTolerance(2)` a 2-letter term scored 12 against an empty column in 2.0, because the empty string is two edits from it, so of two rows tied on the real match, the one with no data in the other searched column ranked first. An empty value scores 0 now.
- **`preset()` leaves out the columns the table doesn't have.** A preset names columns; one the model's table lacks is dropped from the search, and a joined query keeps the columns as given. Columns you pass to `searchIn()` explicitly are untouched.
- **Synonym words ignore case.** `withSynonyms()`, `$searchable['synonyms']`, the `synonyms` config and `synonymGroup()` store each word lower-cased (`mb_strtolower()`), as the term is looked up, so `'Laptop' => [...]` now expands `laptop` and `'Ägypten' => [...]` expands `ägypten` on both paths. Two words that differ only in case are one word, and the later one wins.
- **`ignoreStopWords('en')` prefers the configured list**, which is shorter than the built-in one — see [Tokenizers](#tokenizers-per-model-pipelines-accent-folding-and-stop-word-files-new).
- **A column weighted `0` is no longer searched.** In 2.0, `searchIn(['email' => 0])` only kept `email` out of `_score`: the LIKE and `extended()` searches still matched and counted a row that held the term only there. Now it is out of the search on every path, as on `useInvertedIndex()`: not matched or counted, no `suggest()` table-scan word, and an `extended()` field scope on it is an unknown field. A search whose every column weighs `0` matches nothing. Give the column a weight of 1 or more to keep searching it.

### Exceptions

- **An empty search term throws on every terminal.** `count()`, `paginate()` and `getFacets()` now throw `EmptySearchTermException` for `''` or whitespace, as `get()` always did. If you paginate an empty search box, set `allow_empty_search => true` (every terminal then lists every row) or check the term first. `FuzzySearch::on()` now applies the same rule: its `get()` throws for `''` or whitespace unless `allow_empty_search` is on (2.0 returned the items unsearched).
- **`searchIn()` relation paths need a `Relation` return type or a declared `$searchable` column**, or they throw — see [Relationship search](#relationship-search).
- **Column names are checked in more places.** `orderByFuzzy()` throws `InvalidArgumentException` for a column that is not letters, digits, underscores and dots, and a column name with a trailing newline is rejected by `searchIn()`, `facet()`, `FederatedSearch::searchIn()` and the macros. A `searchIn()` name of three or more dotted segments whose first segment is not a relation throws when the query is built.
- **A secret-named column passed to `searchIn()`, `filter()`, `filterIn()`, `facet()` and `orderBy()`, and the Eloquent `whereFuzzy()`, `orWhereFuzzy()`, `whereFuzzyMultiple()`, `orderByFuzzy()` and `fuzzySearch()` macros throws `InvalidArgumentException`, and so does a `$hidden` column passed to `searchIn()`, `facet()` or `orderByFuzzy()`**, unless the model lists it in `$searchable['columns']`. These names can come from the request, and searching, faceting or fuzzy-ordering on a column the model keeps out of its output (`?field=password&q=$2y$10$a`) reveals its values row by row. Refused everywhere: a name auto-detection treats as a secret (`password` anywhere in it, `token` or `*_token`, a `secret`, `api_key` or `private_key` part, `*recovery_codes`). Refused in `searchIn()`, `facet()` and `orderByFuzzy()` only: a column in the model's `$hidden`, in any letter case, or in the related model's for a relation path (`author.email`). An equality `filter()`/`filterIn()`, a plain `orderBy()` and the `whereFuzzy()`-style macros take a hidden column as before (a `tenant_id`, a sort field). You are affected if your code passes such a column to these methods. To keep it, declare it in `$searchable['columns']`, a relation path as written (`'author.email'`); a model that auto-detected its columns then searches only the declared ones, so list them all. Declaring needs the `Searchable` trait: a model without it cannot allow a secret-named column in the macros (add the trait, or search a Query Builder). A table-qualified macro column is compared as written. The Scout engine's `orderBy()` refuses a secret-named column. The same check runs on `preset()` columns, `searchOn()`'s third argument, a Filament resource's searchable attributes, a Scout `orderBy()` and `FederatedSearch::searchIn()` on a model without the trait, so an app that names a hidden column there throws too. Query Builder searches have no `$hidden` and are not checked.
- **`extended()`/`searchBoolean()` accept exactly `query.max_tokens` tokens.** They threw at the limit, so the default 32 allowed 31; one more than the limit still throws.
- **A search too large even for one LIKE pattern per word and column throws `QuerySyntaxException`** ("The query is too complex…"), before any SQL runs, on every database. That takes over 2,000 word-and-column pairs, for example 32 three-letter words searched with `tokenize()`, each with 40 synonyms, on two columns (32 × 41 × 2 = 2,624 pairs; longer words pass `query.max_term_length` first, which cuts the term). Search fewer words or columns, or declare fewer synonyms. The same applies to `whereFuzzyMultiple()`, the `fuzzySearch()` macro, the `Fuzzy` scopes and `tableSearch()` when they are given more than 2,000 columns, or fewer columns with native functions that bind more than one value each.
- **`didYouMean()` surfaces real database errors**, and `extended()` throws for an unknown field or an empty `field:` — see [Inverted index](#inverted-index-bm25) and [Extended syntax](#extended-syntax--and-field-are-operators-now).

### Caching

- **A published `cache` block is live.** The `cache.*` config is now read (`enabled`, `driver`, `ttl` in seconds, `prefix`). If your `config/fuzzy-search.php` has `'enabled' => true` (as the old README showed), every `get()`, `first()` and `simplePaginate()` is now cached for `ttl` **seconds** in that store. A ttl you wrote as minutes is now read as seconds. A cache hit fires no `FuzzySearchExecuted` event and writes no analytics row. Set `'enabled' => false` to keep 2.0's behaviour. `cache()` without an argument, or `cache(null)`, now caches for `cache.ttl` (3600 s by default, the same 60 minutes as before; `cache(null)` used to cache nothing), and `cache(0)` turns caching off for that query. `getDebugInfo()['cache_ttl']` is in seconds. A cache entry now holds row keys and scores, not models. A hit re-reads the rows by key (one query per 200 rows, `bm25.candidate_chunk`), plus their eager loads, so it works under Laravel 13's `cache.serializable_classes => false`, drops rows deleted since, and applies each request's own visibility and highlighting. Rows of a search with a join, a union, an aliased FROM or a `fromSub()`, or without the key selected, are stored as their attributes instead and served as cached until the entry expires. Entries from 2.0 are never read.
- **Cache keys changed.** A generated key includes more of the query (highlight tags, `withRelevance()`, `debugScore()`, eager-load names, the connection, database, table prefix and PostgreSQL `search_path`) and the whole `fuzzy-search` config, so entries cached by 2.0 are not reused after upgrading, and any later config change starts a fresh set of entries. A key you pass to `cache($minutes, $key)` is used as given. A search with a `customScore()` closure is cached only under a key you name.
- **A cache hit reloads relations.** Cached rows carry no relations, and each hit runs the current request's eager-load queries, with their constraints.
- **Cached join and union rows keep no hidden attributes.** A row stored as attributes (a join, a union, an aliased FROM, a `fromSub()` or a select without the key) is stored without the model's `$hidden` attributes, so after a cache hit `makeVisible()` finds them empty; don't cache such a query if you show hidden columns from it. With a `$visible` list, the attributes outside it are still stored in the cache store (it filters serialisation, and a joined or aliased column must read the same on a hit as on a miss).

### Inverted index, indexing and commands

- **An index-path query (the Scout engine's too) uses at most `query.max_tokens` distinct terms** (32 by default): the first ones are used, the rest ignored, with no exception. Raise `query.max_tokens` if your searches are longer; each term reads up to `bm25.max_postings_per_term` rows.
- **BM25 rankings change where models share words**, and equal scores come back by model key — see [Inverted index](#inverted-index-bm25).
- **Indexing waits for the transaction to commit**, and writes for one row wait for each other — see [Inverted index](#inverted-index-bm25).
- **With `indexing.async` off, an index error no longer fails the save.** It is reported to your exception handler instead — see [Inverted index](#inverted-index-bm25).
- **The indexer indexes the row as stored, not the instance you pass**, and index suggestions skip hidden columns — see [Inverted index](#inverted-index-bm25).
- **Index terms are capped at 191 characters**, and a new migration widens `model_id` to 191 and, on MySQL/MariaDB, moves it to a byte-wise collation: run `rebuild --fresh` for a model whose string keys differ only by case, accents or trailing spaces (while nothing is indexing: see [Flush only while nothing is indexing](#inverted-index-bm25)), and restart long-running workers after migrating — see [Inverted index](#inverted-index-bm25).
- **Commands exit 1 on bad input**, `rebuild` fills metaphone shadow columns, `rebuild --async` needs `job_batches`, and `flush <model>` is `clear <model>` — see [Inverted index](#inverted-index-bm25).
- **Index searches honour `matchAll()` and the columns you name.** On `useInvertedIndex()`, `tokenize()->matchAll()` served every row holding any of the words; a match now holds each word. `searchOn($query, $term, ['name'])`, or a query builder's `searchIn()` with `useInvertedIndex(Model::class)`, matched every indexed column; it now matches the named columns (and postings written before column weighting). A column declared with the model's own table (`posts.title`) and a value of `"0"` are now indexed. Such searches can return other rows than in 2.0.
- **Commands read a class name with a leading backslash** (`"\App\Models\Post"`, as PHP code writes it) as that class: 2.0's `rebuild --fresh`, `clear` and `flush` given one flushed nothing. `clear` and `flush` also clear a model whose class no longer exists, by the name its rows were indexed under.
- **BM25 searches are typo-tolerant by default** and the dictionary is read per model — see [Inverted index](#inverted-index-bm25).
- **The Scout engine ranks with column weights** — see [Weighted BM25](#weighted-bm25-column-weights-on-the-index).
- **Index-path totals count what the pages serve.** In relevance order, past `bm25.max_postings_per_term`, `paginate()->total()` (and Scout's `total`) count the matches the BM25 ranking holds, where they counted every match while the pages past the ranking came back empty; the index path's `count()` counts the same (2.0 ran `count()` on the LIKE path). With `orderBy()` every match is served and counted. The cap applies to the whole model before a filter, so a filtered relevance search can see fewer of its own matches than `orderBy()` does. Raise the cap if your corpus reaches it.
- **A capped BM25 ranking keeps the same matches on every request.** Past `bm25.max_postings_per_term`, the cut kept whichever equally weighted matches the query plan read first, so the ranking, its pages and `total()` could change between two requests with no data change (after an `ANALYZE`, say). Of equal weighted frequency it now keeps those of the lowest `model_id`, so a common word's capped ranking can hold other rows than 2.0's, and its read takes longer. Raise the cap, or use `orderBy()`, to serve every match.
- **`bm25.max_postings_per_term` caps each word on its own.** It was one cap over the rows of every word of the query together, so a common word's rows filled it and pushed a rarer word's matches out of the ranking, the best match (the row holding both) included. Each word's rows are now cut at the cap on their own, and a word in no more of the model's rows than the cap is read whole, so a capped ranking, its pages and `total()` can hold more matches than before. A search of several common words reads up to words × cap rows (typo and prefix expansions and synonyms count as words), where it read the cap; PHP keeps one score per document, not the rows. Lower the cap if such searches read too much.
- **PostgreSQL: the package analyzes the index tables.** `fuzzy-search:rebuild` (for `--async`, once its batch finishes) runs `ANALYZE` on them; the synchronous rebuild also runs `VACUUM (ANALYZE)` on the postings table, best-effort and outside any transaction, so the ranking reads only the postings' primary key index (an `--async` rebuild leaves that to autovacuum: its batch's `finally()` runs inside the last job, under the job timeout). So does the first index write that leaves the postings table past 16 pages, about 1,000 postings (or the commit of the transaction it ran in), and then a write that finds the postings table more than doubled since its last analyze, until they describe about 10,000 postings (an index write runs `ANALYZE` only). Neither runs while the postings table is under 16 pages. A user that does not own the tables gets a warning instead. A failed `ANALYZE` (for example a lock timeout while autovacuum holds a table) is reported to your exception handler, not thrown, except a connection lost inside an open transaction, which is thrown: the transaction went with it. With schema-per-tenant (one connection, `search_path` switched per tenant), each tenant's index tables are checked. After a `pg_restore` or a bulk import into a model's table, run `ANALYZE` yourself (see [Production Setup](bm25.md#production-setup)).
- **The search log migration creates the `analytics.table` table** — see [Search analytics](#search-analytics-new).
- **Single-table inheritance: a rebuild indexes each row under its own class, and a child can share its parent's index.** A rebuild of a parent whose query hydrates child instances (tightenco/parental and the like) indexed each chunk under its first row's class, dropping rows; it now indexes each child row under the child's class, as its saves and deletes always were, so the parent's index search finds the rows hydrated as the parent. To index the hierarchy once, add `public static function searchIndexType(): string { return User::class; }` to each child, run `fuzzy-search:clear` for each child indexed before, and `fuzzy-search:rebuild "App\Models\User" --fresh` — see [docs/bm25.md](bm25.md#single-table-inheritance). A model that already has a method named `searchIndexType()` must make it this static one, returning the class itself or a concrete Eloquent model it extends on the same table and connection (anything else throws a `LogicException`).
- **A plain `fuzzy-search:rebuild` removes the documents of rows that are gone.** After the walk it reads the model's documents, 1,000 at a time, and removes those of rows that writes firing no model events (a query-builder `delete()`, a reseed) deleted, trashed (`SoftDeletes`) or left out of the model's `searchIndexQuery()`. With `--async` the batch's last job does it, in steps of 20,000 documents it adds to the batch. In 2.0 only `--fresh` removed them, and `total()`, the federated counts and BM25's document total counted them. Rows a global scope hides are not removed (a tenant scope in a per-tenant run stays safe); exclude rows from the index in `searchIndexQuery()`. Under single-table inheritance a row that changed kind without model events leaves its old kind's type when the hierarchy's `newFromBuilder()` reads its kind; where only a global scope tells the kinds apart, it stays filed under its old type until its next save or `--fresh`, as in 2.0.1. A model on Scout's `Searchable` keeps the trashed rows Scout indexed while `scout.soft_delete` is on; any other model's trashed rows are removed. For a parallel build use `rebuild --async`; don't split a plain `rebuild` by ranges in searchIndexQuery(), because each run's closing prune removes the documents of rows the hook leaves out.
- **`restore()` re-indexes a soft-deleted model.** A change to the deleted-at column now triggers a reindex; the restored row used to stay out of `useInvertedIndex()` results until the next rebuild.
- **Rebuild your index if you search non-Latin or accented text.** The BM25 tokenizer now keeps
  combining marks (`\p{M}`) attached to their base character instead of stripping them. Indexes
  built from Bengali, Hindi, Thai, or decomposed-accent Latin text before this fix are stale —
  run `fuzzy-search:rebuild "App\Models\YourModel" --fresh` once (while nothing is indexing: see [Flush only while nothing is indexing](#inverted-index-bm25)).
- **Accessor-backed searchable fields reindex on every save by default.** If a searchable column
  is a computed accessor (e.g., a `brand_name` accessor backed by `brand_id`), `wasChanged()`
  can't see it, so previously the model never reindexed after an update. It now reindexes on
  every save unless you declare `$searchable['reindex_on' => ['brand_id']]` to trigger reindexing
  only when the real backing column(s) change.
- **Models with no `$searchable['columns']` are now indexed.** A model that uses the trait and
  declares no columns (`class User extends Model { use Searchable; }`) is now indexed — and gets
  its `*_metaphone` shadow columns maintained — from the columns auto-detection already used for
  `search()`; previously `getSearchableColumns()` returned `[]` and every consumer except
  `search()` silently skipped the model. This only starts writing rows when `indexing.enabled` is
  `true` (it defaults to `false`): if you enable indexing and have such models, their first save
  or `fuzzy-search:rebuild` will now populate the index. Auto-detection selects string-like
  attributes only, and that applies to what a zero-config model **searches** as well as what it
  indexes: a column cast to an enum, `array`, `json`, `object`, `collection` or a custom cast class
  is no longer auto-selected, and neither is an `encrypted` or `hashed` column (its decrypted text
  or hash would otherwise be written to the index and served by `suggest()`), so such a model can search a different set of columns than in v2.0
  (a later string column may take the freed slot). A value that still turns out not to be text is
  skipped rather than thrown, so this cannot make a save throw. Declare `$searchable['columns']`
  to search or index anything else: a declared column is your choice, and one that cannot be
  indexed as text raises an error naming it. An auto-detected column is indexed as the model's raw
  attribute value, not through a get accessor, so an accessor that decrypts or reformats it never
  reaches the index. A masking accessor (`Str::mask()`) is bypassed the same way, so the unmasked
  value is indexed and served by `suggest()` and `didYouMean()`; and encryption that decrypts into
  the attributes in memory (spatie/laravel-ciphersweet) is invisible to the package, so its
  plaintext is indexed. Put such a column in `$hidden`, or declare `$searchable['columns']`.
  Declaring the columns, or overriding `getSearchableColumns()`, is what opts into accessors.
  Only the index reads the stored value: `suggest()`'s table scan, relevance scoring and
  highlighting read an auto-detected column through its accessor, as in 2.0, so for a column an
  accessor decrypts, declare `$searchable['columns']` without it, or hide it (`$hidden`);
  otherwise `suggest()`'s table scan can return words from the decrypted value of rows the query
  can see.
- **Auto-detection skips hidden and secret columns.** A model with no `$searchable['columns']`
  no longer auto-selects a column in `$hidden`, a column outside a non-empty `$visible`, or
  a secret-named column — any name containing `password`; `token` or a name ending in
  `_token`; `secret`, `api_key` or `private_key` as a whole underscore-separated part of the
  name (`secret_note`, `stripe_api_key`, `webhook_secret` — not `secretary_name`); or a name
  ending in `recovery_codes` (in any letter case; `sort_key`-style names are still picked) —
  on the LIKE path as well as the index path. A zero-config model whose only priority column was
  hidden (a hidden `name`, say) now picks another column, or none. With none, the model has no
  column to search, and its search matches nothing (see [Search results](#search-results)).
  Declare `$searchable['columns']` to keep searching a hidden column. Detection reads the model
  class's default `$hidden` and `$visible`, once per process, so a column hidden at runtime with
  `makeHidden()`, `setHidden()` or a per-request `getHidden()` is still searched and indexed; put
  it in `$hidden` to keep it out.
- **Scout: `scout:delete-index` now deletes.** It passed the index name where a model class was
  expected and removed nothing; it now clears every indexed model whose `indexableAs()` is that
  name. A deploy script that runs it before `scout:import` now really starts from empty. The
  engine's `raw()['total']` is also the match count now, not the size of the returned page.

### Federated, Scout and in-memory search

- **The Scout engine cuts `paginate()`, `simplePaginate()` and `take()` to `max_candidates`** (default 1000), as the builder does ([page sizes](#paginate-page-sizes)). A Scout page of more rows is now `max_candidates` rows; raise the key if you really page in bigger slices.
- **`FederatedSearch` searches each model with its own algorithm and typo tolerance.** Without `using()` or `typoTolerance()`, every model that uses the `Searchable` trait was searched with `fuzzy` and a typo tolerance of 2, whatever its `$searchable['algorithm']` and `['typo_tolerance']` said. Each model now searches the way `Model::search()` does, with its own configuration (the configured `default_algorithm` and typo tolerance when it declares none), so a `like` model no longer matches typos in a federated search. `using()` and `typoTolerance()` still apply to every model and `options()`, which used to be ignored, now applies to every model too, and `typoTolerance()` now reaches models without the trait as well. Call `->using('fuzzy')->typoTolerance(2)` to keep the old results.
- **`FederatedSearch` reads the declared columns of models without the `Searchable` trait.** A `Fuzzy`-trait model is searched on its `$fuzzySearchable` (or `getFuzzySearchableColumns()`), and a model with a protected `$searchable['columns']` on those columns; both used to be searched on the guessed `name`/`title`, so results change for such models. A `Fuzzy`-trait model is also searched with its own `$fuzzyAlgorithm` and `$fuzzyOptions` (`default_algorithm` when it declares none) instead of LIKE; call `->using('like')` on the federated search to keep the old matching.
- **`FederatedSearch` holds models without the `Searchable` trait to `max_candidates`.** Such a model contributes at most `max_candidates` rows (default 1000) to `get()`, the paginators and `getCounts()`, as a `Searchable` model always has; its matches used to be counted and fetched without limit, and a deep page fetched offset + perPage rows from it.
- **`FederatedSearch` results are now deterministically ordered.** Ordering is score, then
  `orderByModel()` (or the `across()` order), then primary key — previously ties and
  `withRelevance(false)` results came back in database order.
- **`FederatedSearch::searchIn()` applies to models that use the `Searchable` trait** (it was ignored for them), and columns a table does not have are skipped instead of raising SQL errors. A `Searchable` model with none of the named columns on its table now contributes nothing, and is left out of `getCounts()`, as a model without the trait already was; 2.0 searched it on its own configured columns. One with some of the named columns searches only those. A relation column (`author.name`) counts as none, so a model given only relation columns contributes nothing either.
- **`FederatedSearch::getCounts()` and `paginate()->total()` count reachable matches.** `getCounts()` grouped the page and so reported page sizes; it now returns per-model match counts (0 for a model searched with no match; a model `searchIn()` leaves out has no entry), each capped at `max_candidates` and `limitPerModel()`, and `total()` is their sum.
- **Scout searches honour `where()`, `whereIn()`, `whereNotIn()` and soft deletes.** 2.0 ignored them: a Scout `->where('tenant_id', $id)` returned every tenant's matching rows, and with `scout.soft_delete` on, trashed rows came back without `withTrashed()`. Results and totals now honour those constraints, and trashed rows appear only under `withTrashed()` or `onlyTrashed()`, so a page can hold fewer rows than in 2.0. If you filtered Scout results in PHP to work around this, you can drop that filter. The fields are columns of the model's table, as on Scout's database engine, not keys of `toSearchableArray()`, which this engine never calls: a `where('is_published', true)` on a field that only `toSearchableArray()` has now throws an unknown-column `QueryException` on MySQL, MariaDB, PostgreSQL and SQL Server, and on SQLite raises no error and matches no row. Constrain a real column instead, or drop the `where()`.
- **Scout `hybrid()` throws `NotSupportedException`.** It reached the engine and ran a plain keyword search.
- **A null Scout query matches nothing.** `Model::search($request->input('q'))` passes null for an empty or missing `?q=`, and every terminal threw a `TypeError`; it now returns no rows and a total of 0.
- **A model on the `fuzzy-search` driver needs the package's `Searchable` trait.** With Scout's trait alone (no `getSearchableColumns()` or `searchableText()` hook of its own), searching it now throws `LogicException`, naming the trait, where 2.0.1 returned nothing; indexing it throws that `LogicException` where 2.0.1 threw `BadMethodCallException` on the missing `getSearchableColumns()`. Deleting and flushing it still work, except `delete()` on a `SoftDeletes` model under `scout.soft_delete`: Scout re-indexes the trashed row, so the row is trashed and then the `LogicException` is thrown (2.0.1 threw `BadMethodCallException` there), and the row stays trashed. Add `use Ashiqfardus\LaravelFuzzySearch\Traits\Searchable;` beside Scout's trait, as in the [recipe](integrations.md#usage).
- **A custom Scout key is rejected.** A model that overrides `getScoutKey()` or `getScoutKeyName()` throws `LogicException` when the `fuzzy-search` driver indexes or searches it: the index is keyed by the primary key, so such a model was indexed and then never found. Remove the two methods.
- **Scout `orderBy()` now orders.** `orderBy()`, `orderByDesc()`, `latest()` and `oldest()` on a Scout search were ignored and results came back in relevance order; they now replace the relevance order (ties by key, descending), as on Scout's database engine, and with `scout.soft_delete` on, `withTrashed()` keeps trashed matches in that order. An order column that is not a column name throws `InvalidArgumentException`. The engine also searches only the first `query.max_term_length` characters of a query.
- **Scout `paginate()` counts once (Scout 10.1+).** The engine builds `paginate()` and `simplePaginate()` itself, with the total it has already counted, so a `query()` callback no longer makes Scout read and bind every matching key; that failed on SQL Server past 2,100 matches on a string key. The paginator is the one Scout builds. `paginateRaw()` and `simplePaginateRaw()` now return models, as on Scout's database engine; use `raw()` for the engine's raw result. Under a `query()` callback, `take()` no longer caps `paginate()->total()`. On Scout 10.0, put constraints on `where()`/`whereIn()`, not `query()`; Scout counts `paginate()`'s total itself there, and a `query()` callback's one-to-many join once per joined row, so filter with `whereHas()`.
- **Scout totals honour global scopes in relevance order.** A row a global scope hides no longer counts in `total()`, `hasMorePages()`, `raw()['total']` or `keys()` in relevance order (`orderBy()` already left it out), and the page that held it is now full. A model with a global scope other than `SoftDeletes`' costs one more query per Scout search.
- **A Scout page serves each model once, in order, with its score.** A `query()` callback whose join repeats a model (one-to-many) filled a page with a copy per joined row; the page now holds each model once. A `query()` callback or global scope that `select()`s without the primary key now keeps the relevance or `orderBy()` order and each row's `_score`, where every row scored 0 in the database's order. An override of the model's `getScoutModelsByIds()` still applies; choose columns with `query()->select()`, not in that override's `get([...])`, which now gets every column.
- **The Scout engine's `update()` writes a collection in one transaction**, so an error on one model leaves none of that collection indexed, where before the models ahead of it were.
- **`FuzzySearch::on()` over Eloquent models reads only attributes, casts, accessors and loaded relations.** A dotted `searchIn()` name no longer lazy-loads an unloaded relation for each item; call `load()` on the collection first. A name that is only a method (`reindex`, an app method) is no longer called. See CHANGELOG `### Security`.
- **`FuzzySearch::on()` leaves items that did not match untouched.** It set `_score` and a temporary `_raw_score_tmp` on every item it scored, so a model in your own collection that did not match kept them and failed to `save()` afterwards. Only a matched item is decorated now. Code that read `_score` from an item the search did not return finds none.
- **`FuzzySearch::on()` folds case in every script.** It folded ASCII only, so `ÉCOLE` scored `école` as a near-miss and `МОСКВА` did not match `москва`; such matches now score as exact/prefix/contains matches, so in-memory results for non-ASCII text can rank differently. A term is also cut at `query.max_term_length` characters.
- **`FuzzySearch::on()` ranks a value that holds the term above a near-miss.** A near-miss scored its `similar_text()` percentage (60 to 99), above a prefix match (60) and a contains match (30), so `john` returned `Jon` before `John Doe`. It now scores 0.29 of that percentage, so its `_raw_score` is at most 28.71 and its `_score` falls with it. `in_memory.min_similarity` still reads the percentage.

### Config and PHP API

- **`FuzzySearchExecuted` fires in more places.** A BM25 search that matches nothing fires it, in-memory searches fire it (see [Search analytics](#search-analytics-new)), and `simplePaginate()` reports the page size in `resultCount`, not the look-ahead row.
- **Config keys that were documented but inert now take effect** (`scoring.*`, `highlighting.*`, `performance.max_patterns`, `unicode.normalize`, `similar_text.min_percentage`, `cache.*`, `synonyms`) — see [below](#config-keys-that-now-take-effect).
- **New config keys:** `indexing.job` (`tries`, `backoff`, `timeout`) bounds retries of
  `IndexModelJob`/`RebuildIndexJob`; `bm25.candidate_chunk` (default 200) is the largest ranking an
  ordered index search lists by id on SQL Server, or for a string key on PostgreSQL and a word in
  more than a tenth of the rows (elsewhere it lists a ranking that holds every match, whatever its length), the chunk the index path hydrates a page's rows and a cache hit
  re-reads rows in, and, on SQL Server, for a string key on PostgreSQL or SQLite, or for one over a union
  on MySQL or MariaDB, the chunk a
  constrained relevance search checks a ranking of at most `max(bm25.candidate_chunk, max_candidates)`
  ids in (on another connection than the index, where that subquery cannot run, any length of ranking).
- **`indexing.table` was removed** — see [Removed config keys](#removed-config-keys).
- **`FuzzySearch::$config` is now nullable (`?array`)** and is null when the class is container-built; subclasses that read `$this->config` must call `currentConfig()` instead. The singleton reads `config('fuzzy-search')` live, so a runtime `config([...])` override reaches the drivers.
- **Two protected `SearchBuilder` properties are gone:** `$debounceMs` and `$stopWordLocale`, which `debounce()` and `ignoreStopWords('xx')` wrote and nothing read. A subclass that reads them should stop. `PorterStemmer`, `NullStemmer` and `WhitespaceTokenizer` are no longer `@internal`.
- **TrigramDriver's LIKE fallback cap raised from 10 to 100.** It now caps its pattern list at
  `performance.max_patterns` (default 100) instead of a hard-coded 10, so long terms match more
  widely; lower the key or call `maxPatterns()` to restore the old cap.
- **`SearchBuilder::first()` is declared `Model|\stdClass|array|null` (was `?Model`).** On a query-builder source it returns the row; it threw a `TypeError`. A subclass that overrides it with `?Model` still compiles.
- **`debounce()`, `locale()` and `minMatchLength()` raise `E_USER_DEPRECATED`** — see [Deprecations](#deprecations).
- **Method signatures changed:** `SearchBuilder::calculateRelevanceScores()` takes an optional `?array $terms` second argument (an extended query's leaf terms, scored one by one), and `generateCacheKey()` returns `?string` (null when the search cannot be cached). `SearchBuilder::applyHighlighting()` takes an optional `?array $terms` and `addDebugInfo()` an optional `?string $algorithm` second argument; `BaseDriver::quoteColumn()` and `FuzzySearch::quoteColumnForDriver()` an optional `?\Illuminate\Database\Query\Builder $query` last argument; and `TrigramDriver::trigramsToPatterns()` an optional `string $value` second argument. `FlushCommand::handle()` (`fuzzy-search:flush`) no longer takes an `IndexManager`. In the `@internal` index classes, `IndexManager::removeFromIndex()` lost its third argument, `bool $updateMeta` (it always updates the model's meta row now), `IndexManager::indexBatch()` gained an optional `bool $scout`, and `Bm25Scorer::count()` and `search()` an optional `array $columnWeights`. `SearchBuilder::highlight()`'s first parameter is `?string $tagOrOpen = null` (it was `string $tagOrOpen = 'em'`; null reads `highlighting.tag_open` and `tag_close`). In `FederatedSearch`, the protected property `$typoTolerance` is `?int` (null: each model's own), so a subclass that redeclares it must use that type, and `$searchableColumns` is gone. A subclass overriding one of them must follow: PHP rejects an override that accepts fewer arguments than the method it overrides, or requires more.
- **Subclasses: four protected members are gone or changed.** `FuzzySearch::DRIVER_MYSQL` (a protected constant), `ExplainCommand::analyzePatterns()` and `LevenshteinDriver::applyNativePostgres()` are removed, and `FuzzyDriver::$maxDistance` no longer has a `= 2` default: its constructor sets it from the configuration. A subclass that uses one must declare its own.
- **Scout 10.0 is not supported.** `composer.json` conflicts with `laravel/scout` below 10.1, the first release that hands the engine `paginate()` and `simplePaginate()`; run `composer update laravel/scout` to 10.1 or later (any 10.x from 10.1, or 11.x).
- **Scout 12 is no longer listed.** `composer.json` drops `laravel/scout ^12.0` from `require-dev` and `suggest`; the engine is tested on Scout 10 and 11.
- **A zero-config model's `getSearchableConfig()` no longer returns the `algorithm` and `typo_tolerance` keys** (2.0.1 returned both). Code that overrides or calls this protected method and read them should read `config('fuzzy-search.default_algorithm')` and `config('fuzzy-search.typo_tolerance.max_distance')` instead.

## `_highlighted` is now escaped for every column

- **Every value in `_highlighted` is HTML-escaped as of 3.0.0.** In v2.0 only the
  columns that actually matched were escaped and wrapped in the highlight tag; a searched column
  that did not match carried the raw model value. The array is now uniformly safe to render as HTML.
- **A non-matching value echoed with `{{ }}` is now escaped twice.** `{{ $user->_highlighted['name'] }}`
  on a value containing `&`, `<` or `>` renders the literal text `&amp;`, `&lt;`, `&gt;` instead of the
  characters themselves. Render the array with `{!! !!}`, or use `@fuzzyHighlight($model, 'column')`
  for every column — matched or not — which handles both branches for you.
- **`@fuzzyHighlight` no longer lazy-loads a relation.** For a column the search did not highlight it
  reads an attribute, cast or accessor, or a relation already loaded, and never calls a model method
  named like the column; a relation that is not loaded renders an empty string. Eager-load it
  (`with('author')`) to show `@fuzzyHighlight($post, 'author.name')` for a search that did not search it.

## Config keys that now take effect

Earlier releases documented several config keys as "reserved for future use" — the values
were parsed into the config array but never read by the package. As of 3.0.0 they are read:

| Key | What it controls | v2.0 behaviour | v3.0.0 default |
|---|---|---|---|
| `scoring.exact_match` / `prefix_match` / `contains` / `fuzzy_match` | Base points per match tier, used by both the SQL `ORDER BY` and the PHP rescorer | Ignored — scoring constants were hard-coded | `100` / `80` / `60` / `50` |
| `highlighting.enabled` / `tag_open` / `tag_close` | Default highlight tags, and whether every search is highlighted without calling `->highlight()` | Ignored — tags only came from `->highlight()` arguments | `false` / `<em>` / `</em>` |
| `highlighting.max_matches` | The most occurrences of the term highlighted in one value (`0`: no limit); the rest of the value follows untagged | New key — every occurrence was highlighted | `100` |
| `performance.max_patterns` | Default cap on generated LIKE patterns | Ignored — `maxPatterns()` only stored the value; no driver read it (Trigram sliced at 10 on its own) | `100` |
| `unicode.normalize` | NFC-normalise search terms by default | Ignored — normalization was opt-in per query only | `false` |
| `similar_text.min_percentage` | The least `similar_text()` percentage a `similar_text` match may have, enforced in SQL as a length bound (a match is at most `t·(200 − p) / p` characters for a `t`-character term) | Ignored — `similar_text` matched every value containing the term | `70` |
| `cache.enabled` / `driver` / `ttl` / `prefix` | Cache every `get()`, `first()` and `simplePaginate()` without calling `cache()`; the store; the lifetime in **seconds**; the generated keys' prefix | Ignored — only `cache()` cached, for its own minutes | `false` / `'default'` / `3600` / `'fuzzy_search_'` |
| `synonyms` | Default synonyms (word => its synonyms; case is ignored) for every `SearchBuilder` search except an `extended()`/`searchBoolean()` query, as if `withSynonyms()` were called first; a model's `$searchable['synonyms']` and a query's `withSynonyms()` are merged on top | Ignored — only `$searchable['synonyms']` and `withSynonyms()` reached a search | `[]` |

**If you left these keys untouched** (or never published `config/fuzzy-search.php`), nothing
changes for the first four rows: the new defaults reproduce the same values the PHP scorer already
used internally, so ranking is identical. `similar_text.min_percentage` is the exception: its
default of 70 now applies, so `similar_text` searches return fewer rows (see Behaviour changes).
An untouched `cache.enabled` is `false`, so nothing is cached unless you call `cache()`. An untouched
`synonyms` is empty; mappings you put there now apply to every `SearchBuilder` search except `extended()`/`searchBoolean()`.

That "identical" claim is about the PHP-side rescoring. The SQL `ORDER BY` used while fetching
the initial candidate set is a separate story: it previously used hard-coded weights
(`100`/`50`/`10` for exact/prefix/contains) and now uses the same `100`/`80`/`60` values as
`scoring.*`. On a search that matches more rows than `max_candidates`, that `ORDER BY` decides
which rows make it into the candidate window in the first place — so on tables where matches
exceed `max_candidates`, the candidate window itself (not just its final order) can differ from
v2.0, even with an untouched config.

**If you published the config and edited `scoring.*`** — because the block looked like it did
something — those values now apply for the first time and **will change result ordering**.
Before v3.0.0, the `scoring` block defaulted to `exact_match: 100, prefix_match: 50, contains: 25,
fuzzy_match: 10`, which never matched what the code actually used (`100/80/60/50`). If your
published config still has the old defaults, or your own edited values, review them.

Recommended action: either delete the `scoring` block from your published config (falls back to
the new package defaults), or update it to match the values you actually want, now that it's
live.

**If you published the config, it contains `'normalize' => true`.** That was the v2.0 shipped
value from when the key was inert — harmless at the time, because nothing read it. As of v3.0.0
`unicode.normalize` is live, so a published config will start NFC-normalising every search term
(requires `ext-intl`; it's a silent no-op without the extension). Set it to `false` to keep v2.0
behaviour (also the new package default for a fresh install), or leave it as `true` if you want
normalization.

## Removed config keys

- `performance.chunk_size` — never read; chunk sizing for rebuilds uses `indexing.chunk_size`.
- `performance.debounce_ms` — never read; debouncing belongs on the client (see Deprecations
  below).
- `indexing.table` — the v1 `search_index` table name, unread by v2 outside the deprecated
  `performReindex()` and `fuzzy-search:index` (both keep `search_index` as their default).
- `levenshtein.cost_insert`, `levenshtein.cost_replace` and `levenshtein.cost_delete` — never
  read; no search or score used them. `FuzzySearch::levenshteinDistance()` still takes these costs
  in its own `$options` argument.

Removing these keys from your published config is safe — they had no effect.

## Deprecations

- **`SearchBuilder::debounce()`** — a server-side "debounce" cannot debounce anything: the
  builder only exists for the duration of one request. Calling it now raises
  `E_USER_DEPRECATED` and remains a no-op, as it always was. Debounce on the client instead
  (`wire:model.live.debounce.300ms` in Livewire, or a JS timer around your search input). Will
  be removed in v4.0.0.
- **`SearchBuilder::locale()`** — never selected a stop-word list, a stemmer or a collation: the
  value was only ever folded into the cache key. Calling it now raises `E_USER_DEPRECATED` and
  remains the no-op it always was. Pass the locale where it is actually read —
  `->ignoreStopWords('de')` for a query-time stop-word list, `$searchable['locale']` for a
  model's index pipeline, the top-level `locale` config key for every other model's index. Will
  be removed in v4.0.0.
- **`SearchBuilder::minMatchLength()`** — likewise never read into a pattern or a predicate. Use
  the `min_search_length` config key (whole term) or `typo_tolerance.min_word_length` (per word).
  Raises `E_USER_DEPRECATED`, still a no-op, removed in v4.0.0.
- **`ReindexModelJob`, `BaseDriver::getRelevanceExpression()` and `BaseDriver::getRelevanceBindings()`** have been deprecated since 2.0, with removal announced for v3.0.0. This release removes none of them; the removal is now planned for v4.0.0.
- **`SearchBuilder::partialMatch()`** is *not* deprecated but is documented as a no-op: every
  pattern-based algorithm already searches `%term%`, so substring matching needs no call. The
  `ecommerce` and `exact` presets keep their `partial_match` key; it simply never added anything.

## `paginate()` page sizes

`SearchBuilder::paginate()` now clamps `perPage` to between 1 and `max_candidates` (default
1000) on every search path. Three call sites change:

- `paginate($n)` with `useInvertedIndex()` and `$n` between 101 and `max_candidates` returns `$n`
  rows per page instead of the 100 the BM25 path silently clamped to.
- `paginate($n)` with `$n` greater than `max_candidates` returns `max_candidates` rows per page
  on the LIKE and extended paths, which used to accept any page size while ranking at most
  `max_candidates` rows. Raise `max_candidates` if you really page in bigger slices.
- `paginate(0)` or a negative `$n` returns a one-row page. It used to reach the paginator
  unmodified — `paginate(0)` threw `DivisionByZeroError`.

`SearchBuilder::simplePaginate()` is clamped the same way. It used to accept any page size, and
on the index path `simplePaginate($request->per_page)` hydrated that many models. `take()`/`limit()`
stay your explicit limit and are not clamped: on the index path `take(n)` hydrates `n` models, while
on the LIKE and extended paths the `max_candidates` candidate window still bounds them.
`FederatedSearch::paginate()` and `simplePaginate()` are clamped the same way;
`FederatedSearch::paginate(0)` threw `DivisionByZeroError` too.

## Database fixes you get for free

No code changes required — these are bug fixes in the package itself:

- **PostgreSQL:** BM25 indexing failed on every write with an "ambiguous doc_count" error; the
  inverted index now works correctly.
- **SQL Server:** BM25 indexing threw "This database engine does not support inserting while
  ignoring errors"; meta rows are now created without `insertOrIgnore()`. `didYouMean()` also used
  `LENGTH()`, which SQL Server doesn't have.
- **So on PostgreSQL and SQL Server 2.0.x left the index empty.** The 3.0 migrations find nothing
  to copy there and take seconds, and each indexed model's index needs building once:
  `php artisan fuzzy-search:rebuild "App\Models\YourModel"`.
- **MySQL 8 / PostgreSQL:** `getFacets()` threw (1055 `only_full_group_by` / 42803) on every
  relevance-ordered search, because the relevance `ORDER BY` reached the grouped aggregate. It
  now works on all supported databases, and facets come back highest count first, then by value
  — previously whatever order the database returned.
- **MariaDB:** connections reporting driver name `"mariadb"` (Laravel 11+) now use native
  `SOUNDEX()`, the Levenshtein UDF path, quoted identifiers and the MySQL flush branch —
  previously every MySQL-only branch silently fell back to generic SQL on MariaDB.
- **Several prefixed installs in one schema (PostgreSQL, SQLite, SQL Server):** the index names
  the migrations give themselves now carry the connection's table prefix when `prefix_indexes` is
  on (Laravel's default for MySQL, PostgreSQL and SQL Server; add it to an SQLite connection), so a
  second install with another prefix migrates; it stopped at `relation "postings_unique_idx" already
  exists`. Without a prefix the names are unchanged, and an existing install keeps its own: the
  migrations find each index under either name.

## Relationship search

- Nothing to change for existing calls — table-qualified column names (`table.column`) are unchanged.
- `_highlighted`/`_matches` gain dotted keys only when you search relation columns.
- `AstCompiler::compile()` (internal, `@internal`) gained an optional fourth argument.
- `AstCompiler::__construct()` (internal) gained optional arguments (`int $typoDistance`, `array $fuzzyOptions`, `array $qualified`, `?array $listed`).
- **`searchIn()` relation paths need a `Relation` return type or a declared `$searchable` column.** A dotted segment is followed only when it is a public, non-static method with no required parameters, not defined by Laravel or this package, that declares a `Relation` return type — or when the full path is listed in the model's `$searchable['columns']`. Anything else throws `InvalidArgumentException` naming the fix, before any SQL, without calling the method. Add return types to relation methods you search through (`public function author(): BelongsTo`), or list the path in `$searchable['columns']`. Relations defined by Laravel's own traits (for example `Notifiable::notifications()`) are not followed; wrap one in a method of your own with a return type.
- A dotted name that starts with a table of the query (the FROM table, a joined table, or an alias) is that table's column. If a relation you search through has the same name as a table you join, alias the join.

## Extended syntax: ~ and field: are operators now

`extended()` / `searchBoolean()` gained two operators:

- **`~word`** — a typo-tolerant term, run through the same driver as the rest of the package. It
  follows `typoTolerance()` (default `typo_tolerance.max_distance`, shipped as 2; `0`, or `config('fuzzy-search.typo_tolerance.enabled') ===
  false`, makes it a plain substring match). `~` can't combine with `'`, `=`, `^`, a quoted phrase or a trailing
  `$` — `~word` stands on its own (a field scope in front is fine: `name:~jonh`) — and `~` alone
  throws.
- **`field:term`** — scopes one term to one searchable column: a direct column, a table-qualified
  column matched by its bare name (`users.name` answers to `name:`), or a relation column declared
  in `searchIn()` / `$searchable['columns']` (`author.name:smith`). Any operator can follow the
  colon (`email:^admin`, `name:~jonh`, `!name:bob`, `name:"john doe"`). `field:` with nothing after
  it (`name:""` included), or a field that isn't searchable, now throws `QuerySyntaxException` (the
  second lists the searchable fields).
- **An empty quoted phrase `""` is skipped** like an empty word. In v2.0 it compiled to
  `LIKE '%%'` and matched every row; a query with nothing else now throws `QuerySyntaxException`.

**If an existing v2.0 query started a token with `~` or `identifier:`, it now parses differently.**
Both operators are recognised only at the start of a token (after an optional `!`), so `12:30` and
`jo~hn` are unaffected — but a v2.0 query such as `extended('~5 rating')` or `extended('ratio:1')`
now tries to parse `~5` as a typo term or `ratio:` as a field scope instead of matching the token
literally. Quote the token to keep the old, literal behaviour: `"~5" rating` / `"ratio:1"`.

The casualties you are most likely to have in production are URLs and mail addresses at the start
of a token and `Re:` / `Fwd:` subject prefixes: `extended('http://example.com')` and
`extended('mailto:bob@example.com')` now throw `Unknown search field "http"` / `"mailto"`, and
`extended('Re: meeting')` throws because nothing follows the colon. Quote them to restore the v2.0
substring match: `"http://example.com"`, `"mailto:bob@example.com"`, `"Re:" meeting`.

**A `!` is now NOT only as the first character of a token.** In v2.0 any `!` started a NOT term,
so `extended('yahoo!mail')` meant `yahoo !mail` (excluding the row it named), `=John!!!` searched
for `John`, and a `!` right after another operator dropped that operator: `^!a`, `'!a`, `=!a` and
`!!a` all meant NOT `a`, and `~!a` threw. Anywhere but a token's first character `!` is now part of
the term: `^!a` is a prefix search for `!a`, `~!a` a typo-tolerant term, `!!a` excludes `!a`. For
the old meaning, start the token with the `!`: `yahoo !mail`, `!a`. `name:!john` still throws; its
message now says to write `!name:john`.

A `!` with nothing to negate now throws `QuerySyntaxException` too: one that ends the query, or
is followed by whitespace, `|` or `)`. In v2.0 a `!` that ended the query was ignored. Quote a
lone `!` to search for it: `"!"`.

`useInvertedIndex()` combined with `extended()` still runs the query on the LIKE path — that was
already true in v2.0, it's just visible now: `getDebugInfo()` reports `'algorithm' => 'extended'`
and `'index_ignored' => true` whenever both are set. `count()` and `paginate()` used to disagree
with `get()` here — they took the BM25 index path on the plain search term while `get()` correctly
ran the extended query. All three (plus `simplePaginate()`, which was always correct — it runs
through `get()`) now agree.

## Inverted index (BM25)

- **New migration to run.** `fuzzy_index_terms` gained a `term_length` column — run `php artisan migrate`, then restart your queue workers right away (`php artisan queue:restart`, or `php artisan horizon:terminate` under Horizon). Existing rows are backfilled automatically, and a second `php artisan migrate` after a failed one fills the words still at 0; no index rebuild is required. On MySQL/MariaDB, a worker still running 2.0 code after the migration adds new words with a `term_length` of 0, and typo expansion and `didYouMean()` never reach those words (it also writes postings with no column name, which score at weight 1). If workers indexed during the deploy window before the model terms migration (`2026_10_13_000002`) ran, it fills those lengths in as it counts each model's words. For writes after it, rebuild the models they indexed with `--fresh`: each model keeps its own copy of a word's length (`fuzzy_index_model_terms`), which neither a plain `rebuild` (a word whose count does not change is left as it is) nor `UPDATE fuzzy_index_terms SET term_length = CHAR_LENGTH(term) WHERE term_length = 0` reaches. On SQLite, PostgreSQL and SQL Server a 2.0 worker's index writes fail instead and roll back whole (on SQLite the postings' unique key changed under it; on PostgreSQL and SQL Server 2.0.1's dictionary upsert fails on its own), so the rows they were indexing are not in the index at all: once the workers run 3.0, retry the failed jobs (`php artisan queue:retry all`), or rebuild the models they indexed. A job that 2.0 queued and a 3.0 worker runs indexes its row normally.
- **BM25 searches are typo-tolerant by default.** `useInvertedIndex()` now expands each query term against the dictionary within `typoTolerance()` edits (`typo_tolerance.max_distance` by default, shipped as 2). Call `->typoTolerance(0)` to restore exact-term-only matching. `_score` normalisation itself is unchanged, but rankings can now include near-miss rows that a pre-3.0.0 search would not have returned. A near miss of a word the model's index holds is scored with that word's idf and damped (`bm25.fuzzy.damping`), so it ranks below an exact hit of the same frequency and length, however rare the misspelling (see [docs/bm25.md](bm25.md)). In an index of more documents than `bm25.max_postings_per_term`, a word in more than half of them is never an expansion: there a search for `smith` no longer matches every row that holds `with`. The words you type, prefix completions and synonyms match at any frequency.
- **The dictionary is read per model.** `didYouMean()` offers only terms posted under the
  searched model (it used to offer every indexed model's terms) and returns `[]` for a builder
  with no Eloquent model unless you pass `useInvertedIndex(Model::class)`. Typo expansion and
  `asYouType()` prefix expansion draw their candidates from the model's own terms too, so rankings
  on the typo-tolerant and as-you-type index paths can change.
- **A plain query builder keeps its `where()`s on the index path.** `new SearchBuilder(DB::table('notes')->where(...), app(FuzzySearch::class))`
  with `useInvertedIndex(Note::class)` used to search every row the model can see. It now runs inside
  the model's query, so the builder's wheres and joins apply alongside the model's global scopes.
  The builder must select from the model's table (an alias works: `DB::table('notes as n')`). A
  narrowed `select()` may leave out the primary key: the package reads it beside your columns under
  an alias of its own, which never reaches the rows it returns.
- **A `join()` that narrows the rows counts as a constraint, like a `where()`, and so do a `having()`, a `groupBy()`, a union and a `fromSub()`.** On the index path, `count()` and `paginate()->total()` now count only the models these let through (each once, however many rows a join repeats it in), and `suggest()` / `didYouMean()` treat the query as constrained (see below). A union is read as one derived table, so its parts' matches are served in relevance order and under `orderBy()`. In relevance order a model that a one-to-many join repeats is served once, with the joined columns of the first of its rows the database returns; 2.0 served a copy per joined row.
- **A constrained relevance search checks its ranking by key.** On every database but SQL Server an integer key is checked in one query with the ranked ids inlined, and a string key on MySQL or MariaDB 10,000 bound ids per query (on MySQL 8.0.21 and later, more than 1,000 ids go as a `VALUES` table, which its range optimizer does not give up on, read with `index_merge_intersection` and `prefer_ordering_index` off for that statement); on SQL Server, for a string key on PostgreSQL or SQLite, and for one over a union on MySQL or MariaDB, `bm25.candidate_chunk` still sizes the check (see [New config keys](#config-and-php-api)). No setting changes; a rare term under SoftDeletes or a tenant scope no longer reads the whole model table.
- **`didYouMean()` ranks the closest term first,** then the most common, and its reach scales with
  the term's length (1 edit for 2–3 characters, 2 for 4–5, 3 from 6) instead of a fixed 3: a short
  term gets fewer, closer alternatives.
- **`didYouMean()` now throws on real database errors** instead of swallowing them — it still returns `[]` only when the `fuzzy_index_terms` table itself is missing (e.g. migrations not yet run).
- **Another new migration to run.** `2026_09_20_000001_widen_model_id_on_fuzzy_index_tables` widens `model_id` to 191 characters on `fuzzy_index_postings` and `fuzzy_index_documents`, so string keys longer than a UUID can be indexed. On MySQL/MariaDB it also moves `model_id` to a byte-wise collation (`utf8mb4_0900_bin`, `utf8mb4_nopad_bin` on MariaDB): string keys that differ only by case, accents or trailing spaces (`aBc` and `AbC`, as sqids, hashids or base62 produce, `café` and `cafe`, or `abc` and `abc `) were one key in 2.0, so the second overwrote the first's index entry and the model's counts drifted; rebuild such a model with `--fresh` after migrating (`php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh`). A plain rebuild indexes both keys but keeps 2.0's drift: `total_docs`, the document count BM25 scores against, stays above the model's documents. `--fresh` restores it, and the model's own word counts in `fuzzy_index_model_terms`, which its typo alternatives and suggestions rank by. The dictionary's `doc_count` on `fuzzy_index_terms` is a total across models that no search reads. On SQL Server `model_id` keeps the database's default collation, usually case-insensitive, so two such keys still cannot both be indexed there: a rebuild chunk holding both fails on a primary key of the index (2627) and the rebuild stops at that chunk, leaving it and every later chunk unindexed. Indexing them one at a time leaves only the last one findable.
  - **Cost.** On MySQL and MariaDB the migration copies both tables (`ALGORITHM=COPY`: the column's collation changes, and under utf8mb4 its length prefix grows from one byte to two, neither of which InnoDB can do in place), and writes to each table wait until its copy finishes, so the time grows with the postings. PostgreSQL and SQL Server widen the column in place, as a metadata change; SQL Server also drops and recreates the documents primary key, which rebuilds `fuzzy_index_documents` (one row per indexed record). On a large index, run it in a maintenance window with the indexing workers paused, and restart long-running workers (queue workers, Horizon, Octane) afterwards: the ordered index query reads `model_id`'s collation once per process.
  - **Rollback.** Rolling it back deletes index rows whose key is longer than 36 characters and, on MySQL/MariaDB, rows whose key differs from another only by case, accents or trailing spaces (any two keys the table's collation compares equal), giving back their counts; rebuild those models after rolling back if they must stay searchable.
- **Rankings change for models that share words with another indexed model.** BM25's idf now counts documents within the searched model; before, a word common in another model pulled this model's scores down, below zero in bad cases. No rebuild is needed, and `_score` is never negative now. Equal scores now come back by model key, ascending.
- **Index terms are capped at 191 characters.** If your text has tokens longer than that (long URLs, hashes, base64), run `fuzzy-search:rebuild "App\Models\YourModel" --fresh` (while nothing is indexing: see [Flush only while nothing is indexing](#inverted-index-bm25)): the dictionary holds them whole (or not at all above 255), while queries now look up the first 191 characters. A token longer than `query.max_term_length` (128 by default) is reachable only through a prefix search (`asYouType()`), or after raising `query.max_term_length` above its length: a plain search cuts the query to that length first, and looks up a term the index does not hold.
- **Indexing waits for the transaction to commit.** A save or delete inside `DB::transaction()` is indexed (or its `IndexModelJob` queued) when the transaction commits, and not at all if it rolls back. Only a transaction on the model's own connection holds it back: a save outside one is indexed at once, whatever another connection holds open. `reindexRelated()` schedules its rows the same way. A test that saves inside a transaction and inspects the index before committing now sees nothing. Laravel runs these callbacks immediately under `RefreshDatabase`'s wrapping transaction on Laravel 11+ (and on Laravel 10 releases that ship test-aware after-commit callbacks); on older 10.x releases, index inside the test with `IndexModelJob::dispatchSync()` instead. Writes that fire no model events (`Model::query()->update()`, `insert()`, a query-builder `delete()`, `saveQuietly()`, `Model::withoutEvents()`, raw SQL) are still not indexed. Re-index rows written this way with `fuzzy-search:rebuild`. A plain rebuild also removes the documents of rows such a write deleted or trashed, or that the model's `searchIndexQuery()` leaves out. A row moved out of a global scope keeps its document until `IndexModelJob::dispatch(Model::class, $id)` repairs it (the job removes a row that is gone or hidden) or a `rebuild --fresh`.
- **Index writes for the same row wait for each other.** With `indexing.async` off, a save can briefly wait on the database while another process is indexing the same row: a row lock, released at once if that process dies. In practice the wait lasts as long as the other write's short transaction. MySQL/MariaDB give up after `innodb_lock_wait_timeout` (50 s by default); PostgreSQL (`lock_timeout`) and SQL Server (`LOCK_TIMEOUT`) wait indefinitely unless you set a timeout. Nothing depends on the cache store. Removing a model from the index (a delete through the observer, `IndexModelJob` for a missing row, Scout `delete()`) now also claims its document row, so it waits for a write to that row still in flight. For a model that was never indexed, this costs two extra statements: a placeholder insert and its delete, in the same transaction. Writes for different rows do not wait on this claim, except on SQL Server, where every index write waits for the one in flight (see the next point). On MySQL/MariaDB a batch (a rebuild chunk, or a Scout collection) takes its rows' locks with one point read per id, in id order, sent as a single statement, so parallel batches such as several `rebuild --async` workers lock only their own rows. Writes whose rows share words already in the dictionary take those words' locks in one order, so two writes, each in a transaction of its own, queue briefly on each other instead of deadlocking (a transaction of yours that holds two or more index writes can still deadlock: see the next points). Under heavy contention a write that still hits a deadlock (or, on MySQL/MariaDB, a lock-wait timeout) is tried up to three times, unless it runs inside a transaction of yours, where Laravel does not retry it and the deadlock is thrown (`Illuminate\Database\DeadlockException` out of `save()` or `searchable()`); on MySQL and MariaDB, parallel batches that add the same new words can meet one now and then. A write that loses all three is retried by the queue (`indexing.async`, with `indexing.job.tries` and `indexing.job.backoff`) or reported to your exception handler (sync). Scout's queued import jobs run once, so run their queue workers with `--tries=3` (or set `scout.jobs.tries`, on a Scout version that reads it, as 11.x does).
- **SQL Server: index writes to one index run one at a time.** Each index write (a save's, an `IndexModelJob`, a rebuild chunk, Scout's `update()` and `delete()`) first takes an application lock on its index (`sp_getapplock`, named after the database and the table prefix, so every model type shares it) and holds it until its transaction ends. Parallel writers, such as `rebuild --async` on more than one queue worker, deadlocked on each other's locks until they lost all three attempts and left the index partial. More workers no longer add write throughput on SQL Server: each write, from its document claim (the re-read and tokenizing included) to its commit, waits for the one before it, and only the loading of the next rows runs alongside. The wait follows the connection's `LOCK_TIMEOUT` (none by default), as for the write's other locks; a lock not granted throws a `RuntimeException` naming it. Inside a transaction of yours, the lock is held until your transaction commits or rolls back, and every other index write to that index waits for it. A flush (`flush`, `clear`, `clear --all`, `rebuild --fresh`) takes it first too: it waits for the write in flight, and the next ones wait for its commit.
- **An index error on the sync path is reported, not thrown.** With `indexing.async` off, the index is written after the save's transaction commits, and an error there (a deadlock, a lock-wait timeout, a database hiccup) goes to your exception handler (`report()`) instead of being thrown, so the committed write and your own after-commit callbacks go on. If you relied on `save()` failing when indexing failed, watch your error reporter instead. The report is a `LaravelFuzzySearchException` naming the model and the key (in its message and `context()`; the original error is its `getPrevious()`), and `IndexModelJob::dispatch($model, $key)` repairs that row's index entry. Use it for a deleted row too: a plain `fuzzy-search:rebuild` reads only the rows that still exist, so it leaves a deleted row in the index (only `--fresh` removes it). With `indexing.async` on, a failure to queue the job is reported the same way.
- **The indexer reads the committed row, not the instance you pass.** The package's observer, `IndexModelJob` and `fuzzy-search:rebuild` read it through the model's query, with its global scopes, `searchIndexQuery()` and SoftDeletes: a row that query hides, or a trashed row, leaves the index. The Scout engine's `update()` (so `$model->searchable()`) reads it as Scout's own jobs do: without global scopes, and keeping a trashed row while `scout.soft_delete` is on, so `onlyTrashed()` and `withTrashed()` find it. It still applies the model's `searchIndexQuery()`, filters included. A global scope that depends on the request (a tenant or an auth scope) sees no request in a queue worker, so it can hide rows there: remove it for indexing with `$query->withoutGlobalScope(...)` in `searchIndexQuery()`. Unsaved changes on an instance are not indexed. A rebuild reads each chunk twice: its own load plus one re-read under the claim. The re-read is by key, so a string key must be declared as one, `protected $keyType = 'string';` (`HasUuids` and `HasUlids` declare it): 2.0 indexed such a model left at Eloquent's default `int` key type, and 3.0 finds no row for it on SQLite, fails its index writes on PostgreSQL and SQL Server, and can read other rows on MySQL and MariaDB.
- **Suggestions skip hidden columns.** A model with a `$hidden` (or `$visible`) searchable column no longer offers that column's words from `suggest()` or `didYouMean()`. Matching is unchanged: a search, including its typo and as-you-type expansions, still finds rows by that column. For such a model, rebuild once (`fuzzy-search:rebuild --fresh`) so postings written before 3.0 come back into suggestions.
- **Two or more index writes in one transaction of yours can deadlock, on every database.** The package's observer indexes after the save's transaction commits, but Scout with its defaults (`after_commit` off, no queue) indexes at once, inside the transaction, and so does a `searchable()` you call there. A transaction that saves several searchable models this way keeps the first write's locks (its dictionary words, its model's meta row) until it commits and takes the next write's after them, out of the order every write otherwise locks in, so against other writers it can deadlock on MySQL, MariaDB and PostgreSQL (on SQL Server the first write's index lock, held until your commit, keeps the other writers waiting instead). Laravel does not retry a nested transaction: `save()` or `searchable()` throws `Illuminate\Database\DeadlockException`. Set `scout.after_commit` to `true`, or turn `scout.queue` on with a queue worker (on the `sync` queue connection Scout's job still runs inside the transaction), and index several models after the commit, or once for the collection (`$models->searchable()` is one write). One index write in your transaction does not deadlock with a write of a neighbouring row: on MySQL/MariaDB a re-index deletes and writes only the postings that change, each by its primary key. While a transaction with two or more index writes runs, though, the deadlock it causes can roll back either side: a transaction with one index write can then throw `DeadlockException` too, and now and then a write outside any transaction loses its three attempts (the queue retries it; with `indexing.async` off it is reported). Moving the transactions with two or more writes after the commit protects every writer. On MySQL/MariaDB that write reads the row with a shared lock, so it indexes it as it is now, not as your transaction first read it (related rows are read without one); other writers of the row wait for your commit, and so does an insert into the gap a row deleted meanwhile left, and a transaction that indexes a row it has not updated, then updates it, can deadlock with another transaction indexing the same row.
- **SQL Server:** turn on `READ_COMMITTED_SNAPSHOT` for the database (`ALTER DATABASE … SET READ_COMMITTED_SNAPSHOT ON`, which waits until no other session uses the database: run it in a maintenance window, or add `WITH ROLLBACK IMMEDIATE`, which rolls back the open transactions of the others), or set `scout.after_commit` to `true` (Scout's default is `false`), which defers Scout's own save and delete hooks until the commit. The indexer re-reads a row after it claims the row's index entry. Under SQL Server's default locking read committed, that read waits on a row another transaction has updated but not committed. That transaction may be one that indexes before it commits: Scout with `after_commit` off and no queue, or `searchable()` or `IndexModelJob::dispatchSync()` inside `DB::transaction()`. Its index write in turn waits on the index write lock that write holds, so the two deadlock (error 1205, or the lock request chosen as the deadlock victim). Snapshot reads do not wait. An index write the package runs in a transaction of its own (the observer's, a queued `IndexModelJob`, a rebuild) yields in such a deadlock: it runs at a low deadlock priority, so SQL Server rolls it back and it is retried. One inside a transaction of yours keeps your priority, so there, under concurrent writes to the same rows, the victim can be that transaction, another of yours, or a plain read of those rows. `READ_COMMITTED_SNAPSHOT` is the recommended setting (Azure SQL Database has it on by default): with it, four concurrent writers indexing inside their transactions met no deadlock. A `searchable()` you call yourself inside `DB::transaction()` still indexes at once, whatever `after_commit` says: call it after the commit, or turn on `READ_COMMITTED_SNAPSHOT`.
- **Flush only while nothing is indexing.** Run `fuzzy-search:flush`, `fuzzy-search:clear` and `rebuild --fresh` (which flushes first) while nothing is indexing any model: stop the queue workers that run `IndexModelJob`/`RebuildIndexJob` (a queued job indexes whatever `indexing.enabled` says) and keep requests from saving searchable models. Turning `indexing.enabled` off stops only the package's observer, not queued jobs or the Scout engine. On PostgreSQL and SQL Server a flush holds index writes off itself: it waits for the ones in flight and makes new ones wait until it commits, so a write during it lands after it (on PostgreSQL searches go on). `clear --all` does so on every database (MySQL and MariaDB from the moment they hold the tables: a write that commits between their tries to take them is emptied with the rest; their batched DELETEs, below, from their last transaction), and where it truncates (see A large index, below) searches wait for it too. On MySQL, MariaDB and PostgreSQL it never waits for a transaction of yours that has read the index (MySQL waits a second at most, and only while `performance_schema` shows no other session holding the tables; where it cannot read that, it does not try): where it cannot take the tables (MySQL and MariaDB try 3 times, 2 s apart), it deletes row by row. On MySQL and MariaDB those DELETEs, and those of a flush of one model (which truncates only when its model is the only one indexed), run in transactions of about 20,000 rows each, so the rebuild after them does not crawl behind the purge of one huge transaction. Their last transaction waits for the index writes in flight, holds new ones off, deletes what a write between the batches left and counts its words again, so the index ends as one transaction would leave it: emptied, every count exact. A flush interrupted part way is finished by running the same command again, before any rebuild or other indexing (until then a rebuild without `--fresh`, or a save that is indexed, counts the documents it has not reached a second time; the commands say so when they fail), and after such a `clear --all` of a large index, run it again when the index is idle, so it truncates, before you rebuild. A flush gives back the flushed model's share of each word's `doc_count`, then deletes every word no model's index uses any more, whichever model it came from. A write for another model that reuses a word the flush is deleting is not safe either. On MySQL/MariaDB the write keeps the word (it inserts it again if the flush deleted it first), but the two can deadlock (the write retries, and the flush can be run again). If something did index during a flush, rebuild the models it indexed. `fuzzy-search:flush <model>` is now exactly `fuzzy-search:clear <model>`.
- **`fuzzy-search:rebuild` fills metaphone shadow columns** for existing rows, and `rebuild --async` stops before touching the index if the `job_batches` table is missing (`php artisan make:queue-batches-table`, Laravel 10: `queue:batches-table`).
- **Commands exit 1 on bad input** (a class that is not a usable model, `--iterations` below 1, an `add-shadow-column --type` other than `metaphone`). Scripts that relied on exit 0 there will now stop.
- **MySQL/MariaDB: a second new migration rewrites `fuzzy_index_terms`.** The `term` column moves to `utf8mb4_bin`, so `café`/`cafe` (and `résumé`/`resume`) are distinct dictionary terms as they always were on PostgreSQL and SQLite (SQL Server: next item) — indexing a document containing both previously failed with "Undefined array key" (B25). The dictionary becomes accent- and case-sensitive on MySQL/MariaDB; the tokenizer lowercases every term, so searches are unaffected. Run `php artisan migrate`, then rebuild any existing index — `php artisan fuzzy-search:rebuild "App\Models\YourModel"` — because variants the old collation collapsed into one dictionary row stay collapsed until the index is rebuilt.
- **SQL Server: a third new migration rewrites `fuzzy_index_terms`.** `2026_09_30_000001_binary_collation_on_fuzzy_index_terms_term_on_sqlsrv` moves the `term` column to `Latin1_General_100_BIN2`, and drops and recreates every index on it (the unique key, and any you added). Under the database's collation (`SQL_Latin1_General_CP1_CI_AS` by default) the dictionary folded words the tokenizer keeps apart: `straße`/`strasse`, `cœur`/`coeur`, `m²`/`m2`, full- and half-width forms, hiragana and katakana, and under an accent-insensitive (`_AI`) collation `café`/`cafe` as well. A rebuild over rows holding both spellings failed on the unique key (2627); saving them one at a time raised the first spelling's `doc_count` and indexed nothing for the second, so a search for it missed those rows; a row holding both was left out of the index. After `php artisan migrate`, run `php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh` for each indexed model: the postings the old collation dropped are missing until then. The migration touches only the dictionary (one row per distinct word), and a second run does nothing.
- **Another new migration rewrites the postings table.** `2026_10_02_000001_compact_fuzzy_index_postings_table` copies `fuzzy_index_postings` into a compact table clustered by word, keyed by `(term_id, model_type_id, model_id, column_id)`, with each document's length in its postings: a common word becomes one sequential read, and the ranking reads no other table. Search results do not change.
  - **Cost.** It reads the model types from the documents, copies the postings one range of their ids at a time (each range committed with its progress mark, its column names read from the range), builds the secondary index and the foreign keys, and on PostgreSQL vacuums the new table: about 22 minutes for the whole migration at 6M rows (96M postings) on MySQL, and 1 hour 45 minutes for 24M rows on PostgreSQL for an index a pre-release 3.0 build wrote (both on 67be9e1, before the migration's later fixes): from 2.0.x the index on PostgreSQL and SQL Server is empty, and the copy takes seconds. On MySQL at 6M rows a rollback took about as long as the upgrade (22 m 15 s up, 22 m 17 s down; 67be9e1); at 1M rows the rollback of every 3.0 migration to the 2.0.1 layout took 4 m 36 s (7c96ec9). An upgrade straight from 2.0.1 also runs the `column_name` and `model_id` migrations on the same table first, so `migrate` also swaps the postings' unique key in place (`column_name`) and, on MySQL and MariaDB, copies the table when it widens `model_id`. Until the old table is dropped the copy needs room for the new one, about two thirds of its size.
  - **Index searches fail while it runs.** The new code reads the new tables, which are complete only once it has finished: its index searches fail from the migration's first second (`fuzzy_index_model_types` doesn't exist, then an unknown column `model_type_id`). The old code's index searches go on until the swap at the end, when the old table is dropped and the new one takes its name, and fail from then. Run it under `php artisan down`, or deploy so the new code serves requests only after `migrate` has finished. Restart queue workers (Horizon) and Octane after migrating, and after a rollback: they remember the dictionaries' ids, which `down()` drops and `up()` numbers afresh, so a process kept alive across either writes and reads the wrong ones.
  - **Hold the index writes off while it runs.** Stop the queue workers that index, and keep saves of searchable models off (maintenance mode), as for the earlier index migrations. A write made by the old code while the copy runs reaches the old table only. Once its ranges are copied, the migration copies again, whole, each row the old code indexed meanwhile, following such writes for up to five rounds; a removal leaves nothing to follow (the removed row keeps its postings), a write still uncommitted when a round looks for them can be missed (its row keeps the postings copied before), and a write after the last round is lost with the old table. A flush meanwhile (`flush`, `clear`, `rebuild --fresh`) deletes the words its model alone used, some of them copied already: the migration deletes the copied postings of words the dictionary no longer has before it adds the foreign keys. If the index changed while it ran, the migration says so, in the log and on the console, naming each model it touched: run `php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh` for each of them.
  - **A large index.** Let the migration copy it: that is the default route at every size (the whole migration took about 22 minutes for 6M rows on MySQL; for an index a pre-release 3.0 build wrote, 1 hour 45 minutes for 24M rows on PostgreSQL; both on 67be9e1). To skip the copy instead, empty the index first, migrate, then run `php artisan fuzzy-search:rebuild "App\Models\YourModel"` for each model (a plain rebuild: the index is empty, and the workers can be back on while it runs): the migrations have nothing to copy, and the rebuild writes the new layout directly, but searches of a model find nothing until its rebuild finishes. With 3.0 installed, empty it with `php artisan fuzzy-search:clear --all`, which works before the migration too (3.0's `flush` and `clear <model>` read the new dictionaries, which do not exist until the migration has run). How it empties them depends on the database. PostgreSQL, MySQL and MariaDB truncate the postings, the documents, each model's words and (unless a table of yours has a foreign key to it) the dictionary (PostgreSQL all five tables) in moments, unless the tables stay busy or TRUNCATE is refused. PostgreSQL takes them with `NOWAIT`, five tries 200 ms apart. MySQL and MariaDB try 3 times, 2 s apart; MySQL, whose `LOCK TABLES` has no `NOWAIT`, waits a second at most per try, and only while `performance_schema` shows no other session holding one of the tables (where it cannot read that, it does not try). SQL Server truncates them behind its index write lock, then deletes the meta rows and the words, quickly once the postings are gone. A database user without the privilege TRUNCATE needs (`DROP`, and `LOCK TABLES`, on MySQL and MariaDB; `TRUNCATE` on PostgreSQL; `ALTER` on SQL Server) makes it delete row by row too. On a large index that is slow and fills the database's log; MySQL and MariaDB delete in transactions of about 20,000 rows each, so the rebuild after them does not crawl behind the purge of one huge transaction, and a clear interrupted part way is finished by running the same command again, before any rebuild or other indexing (until then a rebuild without `--fresh`, or a save that is indexed, counts the documents it has not reached a second time; the commands say so when they fail). The command says when it deleted row by row: on a large index, run it again when the index is idle, so it truncates. With 2.0.1 still installed, truncate the package tables yourself, while nothing is indexing (with your table prefix in front of each name):
    - PostgreSQL: `TRUNCATE TABLE fuzzy_index_postings, fuzzy_index_documents, fuzzy_index_meta, fuzzy_index_terms;` and, once 3.0 has migrated, `fuzzy_index_model_terms` in the same list (its foreign key references the words).
    - MySQL, MariaDB and SQL Server: `TRUNCATE TABLE fuzzy_index_postings; TRUNCATE TABLE fuzzy_index_documents; DELETE FROM fuzzy_index_meta; DELETE FROM fuzzy_index_terms;` and, once 3.0 has migrated, `TRUNCATE TABLE fuzzy_index_model_terms;` before the words' DELETE, which would otherwise delete its rows one by one. The postings go first: their foreign key references the words, which therefore cannot be truncated, and the words' DELETE is quick once the postings are empty. `FOREIGN_KEY_CHECKS=0` is not needed.
  - **What it checks.** A posting whose document row is missing (an index left inconsistent) has no length to carry, and is dropped; the migration logs how many (`fuzzy-search: the compact postings migration dropped …`). If the migration stops part way, run `php artisan migrate` again: it goes on after its last committed range (a range and its progress mark commit together), and a posting written twice meanwhile is copied once. The run that goes on cannot tell what the old code wrote during the stopped run or since, nor which postings that run dropped, so it warns, naming every indexed model: run `php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh` for each of them. `php artisan migrate --pretend` prints the statements that create and drop the tables; the copy's statements map the names each range holds, so it does not print them. On an install of an earlier 3.0 build it also moves the documents' `model_id` to the NO PAD binary collation (MySQL/MariaDB), as the migrations now do on a fresh install, and replaces that build's `(term_length, doc_count)` dictionary index with the `(term_length, doc_count, id)` one `2026_10_20_000001` drops.
  - **Rollback.** `migrate:rollback` copies the postings back into the earlier layout (restart queue workers and Octane after it, as above). Rolling back an earlier postings migration on its own (`--path`) refuses while the compact layout is in place, naming this migration: roll it back first. It refuses in turn while `fuzzy_index_model_terms` exists, naming `2026_10_13_000001_create_fuzzy_index_model_terms_table`.
  - **PostgreSQL 11 or later** (the primary key `INCLUDE`s `frequency` and `doc_length`).
- **Two more new migrations count each model's words.** `2026_10_13_000001_create_fuzzy_index_model_terms_table` creates `fuzzy_index_model_terms`: one row per model and word it indexes, with its own document count, which every index write keeps in step from then on. `2026_10_13_000002_backfill_fuzzy_index_model_terms_table` fills it from the postings of an existing index (about 3 minutes for 6M rows on MySQL, on 81bedf8; for an index a pre-release 3.0 build wrote, 33 minutes for 24M rows on PostgreSQL with a cold cache, on c2b2c1d, and 11 with a warm one, on 81bedf8, and 70 s for 1M rows on SQL Server, on 81bedf8; all before 8274a49 changed how it sets a range's words left at length 0; 15 s at 1M rows on MySQL on 7c96ec9). It counts a range of words at a time, each range committed with its progress. If it stops part way, run `php artisan migrate` again: it goes on after its last committed range, and warns, naming every indexed model to rebuild with `--fresh`. If the index was written while it ran, it logs and prints a warning naming each model to rebuild with `--fresh`. A model's typo expansion, `asYouType()` prefixes, `suggest()`, `didYouMean()` and BM25 document frequency read it, so another model's words no longer slow them (1M product SKU codes made every users typo search read all of them). Expansions and suggestions are now the model's own most common words by its own count, so rankings on the typo-tolerant and as-you-type index paths can change. Run both before serving the new code, as for the compact migration: until the backfill has finished, a model's reads find only the words written since the first of them, and BM25 takes a word the backfill has not counted yet as held by one document. Rolling back drops the table.
  - **Hold the index writes from the migration until the new code serves.** Code from an earlier 3.0 build keeps writing the index without error once it has run, but does not update `fuzzy_index_model_terms`, so typo and prefix searches miss the words it writes. Stop the queue workers that index and keep saves of searchable models off from `migrate` until the new code serves, or run `php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh` for each model afterwards.
- **One more new migration replaces two indexes.** `2026_10_01_000001_rework_fuzzy_index_terms_and_postings_indexes` adds `(term_length, doc_count, id)` to `fuzzy_index_terms`, in place of the `term_length` index of `2026_09_17_000001`, which `2026_10_20_000001` below drops again: no search reads either, since the typo expansion and `didYouMean()` read each model's own words through `fuzzy_index_model_terms`. It also drops `postings_term_model_idx`, whose columns `postings_unique_idx` starts with. The new index is built from the dictionary, one row per distinct word: a read of the dictionary, one row per distinct word. MySQL and MariaDB build it online; PostgreSQL and SQL Server hold index writes to the dictionary until it is built, while searches go on; each step of the migration commits on its own, so a held write goes on as soon as the index is built. Dropping the postings index is quick. Rolling it back recreates both indexes, and recreating `postings_term_model_idx` reads the whole postings table (it reads the whole postings table).
- **The last new migration drops that dictionary index.** `2026_10_20_000001_drop_term_length_index_from_fuzzy_index_terms_table` drops `(term_length, doc_count, id)` from `fuzzy_index_terms`, on a new upgrade and on an install of an earlier 3.0 build alike. No search reads it, and every index write that changed a word's `doc_count` kept it up. Dropping it is instant: it reads no rows. Rolling it back builds it again (a read of the dictionary, as above).
- **One more new migration marks a flush that did not finish.** `2026_10_22_000001_add_flushing_since_to_fuzzy_index_meta_table` adds a nullable `fuzzy_index_meta.flushing_since` (one row a model: instant on every database; rolling it back drops the column). On MySQL and MariaDB, which commit a flush or `clear` in batches, the flush sets it on the model's meta row first and its last transaction deletes the row. If the flush dies part way, the mark stays: `fuzzy-search:rebuild` of that model (without `--fresh`) refuses, and `fuzzy-search:status` names it, until you run the same command that failed again (`fuzzy-search:clear "App\Models\X"`, `fuzzy-search:flush`, or `rebuild --fresh`). A plain rebuild would find the documents the flush had not reached without their postings and count their words a second time. **Keep the queue workers that index the model stopped until that command has finished:** the mark does not hold saves off, and a save of a half-flushed model counts the same way. PostgreSQL, SQL Server and SQLite flush in one transaction, so the mark is never left set there.

## Weighted BM25 (column weights on the index)

- **New migration to run.** `fuzzy_index_postings` holds one posting per `(term, column)` — run `php artisan migrate`. After the compact layout migration the column is stored by id (`column_id`, through the `fuzzy_index_columns` dictionary); there is no `column_name` column. Existing postings get the empty column `''` and score at weight 1. Until you rebuild, rows re-indexed after the migration (every save through the observer) carry weights while untouched rows stay at weight 1, so mixed results skew towards recently saved rows — rebuild promptly. `php artisan fuzzy-search:status` shows how many rows are still unweighted (`php artisan fuzzy-search:status --legacy` on an index of more than 1,000,000 tokens, where that check, which reads every posting, is skipped by default).
- **Plan it on a large index.** The migration swaps the postings unique key for a four-column one, and that is a whole-table index build — PostgreSQL holds a lock that blocks writers on `fuzzy_index_postings` for the duration, and the rebuild then rewrites every posting. Run the migration in a maintenance window with the queue workers that index paused (see the [Upgrade checklist](#upgrade-checklist)). If the migration stops part way (a lock-wait timeout, a killed deploy), run `php artisan migrate` again: it does only what is left, and on MySQL and MariaDB the key swap is one `ALTER TABLE`, which InnoDB applies whole (the column is added before it, instantly). `php artisan migrate --pretend` lists the statements the upgrade from 2.0.1 runs, for every 3.0 migration.
- **Rebuild each model to get weighted ranking.** `php artisan fuzzy-search:rebuild "App\Models\YourModel"` writes one posting per `(term, column)`, letting `searchIn()`/`$searchable['columns']` weights scale each column's term frequency before BM25 saturation (BM25F-lite). A plain rebuild is enough, and it can run while the app indexes: it re-indexes each row in place, replacing its `''`-column postings, and writes for the same row wait for each other. `--fresh` also drops rows that left the table without a model event, but it flushes first, so run it only while nothing is indexing (see [Flush only while nothing is indexing](#inverted-index-bm25)). `php artisan fuzzy-search:status` lists any model still carrying un-rebuilt (`''`-column) postings (with `--legacy` past 1,000,000 indexed tokens).
- **Rankings on the index path change for every model with unequal column weights, including zero-config ones.** Auto-detected columns already carry weights (e.g. `name` 10, `email` 8), so a plain `Model::search(...)->useInvertedIndex()` call can return results in a different order once you rebuild, even though you configured nothing yourself.
- **Opt out and keep v2.0 ordering** by passing equal weights, e.g. `->searchIn(['name' => 1, 'email' => 1])` — `searchIn()` overrides the weights it names and leaves the model's other `$searchable['columns']` weights in place, so list every weighted column.
- **The Scout engine ranks with the same column weights as `useInvertedIndex()`.** It reads the same postings and weighs each column by the model's `$searchable['columns']` weights (`Searchable::getSearchableColumnWeights()`), so after you rebuild, Scout rankings change for every model with unequal column weights — zero-config models included, since auto-detected columns carry weights (`name` 10, `email` 8, …). A model that declares `getSearchableColumns()` itself without the package's `Searchable` trait weighs every column 1, and postings written before the rebuild (`''` column) weigh 1. A model with neither throws `LogicException` on the Scout driver.
- **`migrate:rollback` deletes per-column postings.** Rolling back the `column_name` migration removes every posting row that isn't `''`-column (see the migration's `down()`); then, on 2.0.1, run `fuzzy-search:rebuild "App\Models\YourModel" --fresh` once for each model to restore a working index. Run it once only: 2.0.1's flush leaves the flushed model's documents in the `doc_count` of every word another model also holds, so each further `rebuild --fresh` (or `flush` and rebuild) of a model counts its words again, which skews 2.0.1's BM25 ranking and `didYouMean()` order. That is a 2.0.1 defect: 3.0's flush counts those words again from the other models.

## Search analytics (new)

- **New migration to run.** `php artisan migrate` creates the table `analytics.table` names (`fuzzy_search_logs` by default). Set `analytics.table` before you migrate, because the migration and the recorder both read it. The table sits there with no effect until you set `analytics.enabled` to `true` in `config/fuzzy-search.php`; `migrate:rollback` drops it again.
- **`FuzzySearchExecuted` gained three parameters:** `resultCount` (int, `-1` = unknown), `path` (`like`|`bm25`|`extended`|`in_memory`) and `modelClass` (`?string`, `null` for query-builder and in-memory searches). All three are appended with defaults, so an existing five-argument listener or third-party dispatcher keeps working unchanged.
- **In-memory searches now fire `FuzzySearchExecuted` too.** `FuzzySearch::on($items)->search(...)->get()` previously fired nothing; it now dispatches the same event (`path: 'in_memory'`, `modelClass: null`). If you have a listener that counts or logs this event — including the persisted analytics listener below — it now also sees in-memory searches, so counts recorded after upgrading will be higher than before if your app uses `FuzzySearch::on()`. An in-memory search with an empty term or no `searchIn()` columns still fires nothing, same as v2.0.
- See [Persisted Search Analytics](analytics.md#persisted-search-analytics) for the opt-in `fuzzy_search_logs` recording, the `SearchAnalytics` query API and the two `fuzzy-search:analytics*` commands — none of this runs unless you enable `analytics.enabled`.

## `suggest()` on an indexed model now completes from the dictionary

- **Completions changed for indexed models.** In v2.0, `suggest()` always scanned the table and returned column values as stored. As of v3.0.0, when the model has a `fuzzy_index_meta` row (it has been BM25-indexed), `suggest()` instead completes the last word of the term from that model's dictionary — completions are **lower-case dictionary terms**, not the column value as written, and any earlier words in a multi-word term are kept as typed (`"Bob jo"` → `"Bob john"`).
- **Constrained queries keep the table scan.** When the base query carries a `where()`, a `join()`, a `having()`, a `groupBy()`, a union, a `fromSub()`, a forwarded scope or a global scope other than `SoftDeletes`, the default `'auto'` mode uses the table scan even on an indexed model, because the dictionary is scoped to the model, not to the query. `->suggestFrom('index')` forces the dictionary and ignores those constraints. With `indexing.async` (the default) a trashed row's terms leave the dictionary only when the queued index job runs.
- **Restore v2.0 behaviour** by calling `->suggestFrom('table')`, which forces the table scan regardless of whether the model is indexed.
- Un-indexed models are unaffected — they always used, and still use, the table scan.
- **`filter()` and `filterIn()` narrow suggestions too.** `suggest()` and `didYouMean()` keep only what the filtered search could return, so a tenant written as `filter('tenant_id', $id)` is no longer offered another tenant's words. Under a filter, `'auto'` uses the table scan.
- **The limit is cut to 50** for `suggest()` and `didYouMean()`, so a `?limit=` from the request cannot multiply their queries.

## Tokenizers, per-model pipelines, accent folding and stop-word files (new)

- **Nothing changes by default.** The global tokenizer stays `WhitespaceTokenizer`, the global stemmer stays `NullStemmer`, `indexing.accent_insensitive` stays `false`, and `stop_words` gained four locales (`it`, `pt`, `nl`, `ru`) that only apply if you opt into them. An untouched v2.0 config indexes and searches exactly as before — with two edges: (1) when `unicode.accent_insensitive` is on or you call `accentInsensitive()`, the LIKE path now folds characters the v2.0 map did not know (`Ž`→`Z`, `ő`→`o`, `ệ`→`e`, Cyrillic `й`→`и` and `ё`→`е`, Turkish `İ`→`I`) whenever `ext-intl` is loaded — on SQLite and binary collations a term typed with such a character no longer matches a row that stores it, exactly as `café` already behaved in v2.0; (2) a stop word written with capitals in `config('fuzzy-search.stop_words')` is now lower-cased before use, so it is removed where in v2.0 it silently never matched.
- **Each of the three opt-ins requires a rebuild once you turn it on:** `indexing.tokenizer` / `$searchable['tokenizer']` (`NgramTokenizer`, `ScriptAwareTokenizer`), the per-model pipeline overrides (`$searchable['stemmer']`, `['stemmer_language']`, `['locale']`), and `indexing.accent_insensitive`. Each changes what ends up in the dictionary for the model(s) it applies to, so old postings stay stale until you run `php artisan fuzzy-search:rebuild "App\Models\YourModel" --fresh`. See [Tokenizers](tokenization.md#tokenizers), [Per-Model Pipelines](tokenization.md#per-model-pipelines) and [Accent Folding on the Index](tokenization.md#accent-folding-on-the-index).
- **`IndexManager::processTerms()` gained two optional parameters,** `?array $stopWords = null` (words added to the configured stop-word list for that call) and `?string $modelClass = null`, so query-time tokenizing/stemming/stop-word processing can run through that model's pipeline instead of the global default. The existing one-argument call keeps working unchanged; `SearchBuilder` and the Scout engine already pass the model automatically, so this only matters if you call `processTerms()` directly.
- **`ignoreStopWords('en')` (or any locale code) now prefers the configured list.** It reads `config('fuzzy-search.stop_words.{locale}')` first and only falls back to the builder's built-in list when that config key is absent. Out of the box this changes `en`: the shipped config's `en` list has 14 words, the builder's built-in `en` list has 36 — so `ignoreStopWords('en')` now drops fewer stop words than it did in v2.0. If your app relies on the old, larger built-in list, pass it explicitly as an array (`ignoreStopWords(['the', 'a', 'an', ...])`); an array argument is never affected by this change and always replaces the configured list, as before.
- **`Pipeline` (`Ashiqfardus\LaravelFuzzySearch\Indexing\Pipeline`) is `@internal`.** It's the shared tokenize → fold-accents → drop-stop-words → stem sequence behind `IndexManager::pipelineFor()` and `processTerms()`. Construct it only through `IndexManager`; its shape may change without a major version bump.

## Filament integration, JSON API resources and `lastExecution()` (new)

- **New required dependency: `illuminate/http`.** It's present in every Laravel application already, so there is nothing to install; the package's `composer.json` now lists it as a direct requirement instead of an implicit one, backing the new `FuzzySearchResource` / `FuzzySearchCollection` classes.
- **The JSON resources are new, not a behaviour change.** `_score`, `_raw_score`, `_highlighted`, `_matches` and `_model_type` were always plain attributes on the model or array a search returns — a bare `Model::search()->get()` call is unaffected. `FuzzySearchResource` and `FuzzySearchCollection::fromBuilder()` are simply the tidy way to shape that into an API response; adopting them is optional.
- **Two new namespaces:** `Ashiqfardus\LaravelFuzzySearch\Integrations\Filament` (the `HasFuzzyGlobalSearch` trait) and `Ashiqfardus\LaravelFuzzySearch\Http\Resources` (`FuzzySearchResource`, `FuzzySearchCollection`).
- **`SearchBuilder::lastExecution(): ?FuzzySearchExecuted`** returns the event built by the most recent `get()`/`paginate()` call on that builder instance — `null` before either runs, and `count()` never sets it.
- See [Filament Integration](integrations.md#filament-integration), [JSON API Resources](integrations.md#json-api-resources) and [Livewire Recipe](integrations.md#livewire-recipe).
